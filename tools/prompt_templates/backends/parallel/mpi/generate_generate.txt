@@ target_lowering_floor
For a `cpu` target whose `parallel.backend` is `mpi` and whose language is `fortran`, the program runs as several processes started by the target's launcher — `execution.ranks` for the certifying run, and from two up to it in the further runs of the profile's `execution.sweep` — arranged in a two-dimensional process grid the HOST chooses, and the host re-runs the program as ONE process for its quality check; every run must reach the same verdict over its captures. The host-rendered driver distributes each case: it reads the whole case on every rank, partitions the spatial axes the IR's `drive.distribute` declares (axis k along grid dimension k), copies each array that carries an axis into the block of the rank that owns it — the owned cells, plus the ghost margin of a ghost-extended array, already filled from the case — and calls your operations on that block; it gathers what they write onto one rank at each capture, reduces each call's logical result over the ranks so a refusal on one rank is the refusal on every rank, and runs a case too small to split with every rank holding it whole. On a distributed case every rank-0 integer bound directly to an axis's cell count receives the BLOCK's count (and one bound to its ghost-extended count the block's count plus twice the ghost width), so an operation sees its block as a whole case of that size; the case's own count reaches an operation only through a `derived` binding, and the block's first global index through `block.<axis>.first`. So a `component`'s published operations compute exactly what the spec says over the arrays they are handed, and a component's model source names no harness operation at all (an operation that partitions, exchanges, asks the grid or reduces inside itself distributes an already distributed block a second time, and the `Generate.gate` static check refuses it). A `problem`'s `__step` works on its block (its local extents), over ghost-extended temporaries of its own: before every stencil read that crosses a partitioned axis it fills their ghosts with `call <harness>__exchange_halo_r<k>(...)` along that axis's grid dimension, with `periodic` from the spec's boundary rule for that axis (the exchange is what a periodic copy of the edges becomes), along dimension 1 first and then dimension 2 when a stencil reads a corner (the second exchange carries the halo cells the first one filled); `<k>` is the array's rank, 1 to 3, and on rank 2 and 3 `axis` names the array's axis partitioned along that grid dimension, so an array of rank 3 with one axis that is not partitioned, at whatever position (a vertical or a component axis beside the two horizontal ones, as in `(ka, ia, ja)`), is exchanged whole, one call per grid dimension, and an array of rank 4 is exchanged one slice of an unpartitioned axis at a time over the rank-3 exchange; it then restores each wall side by GLOBAL index — the lower wall of axis k where `block.<axis>.first` is 1, the upper where that index plus the local count minus 1 is the case's count — and leaves the periodic and neighbour sides to the exchange, never deciding a wall by `<harness>__grid_coord` (a case every rank holds whole has both walls on every rank). Its `__init` computes what depends on position from the block's first global index and the case's counts. The halo exchange requires every rank to own at least `ng` cells along the dimension it exchanges along (the harness stops the run otherwise). The message-passing runtime is reached ONLY through the target's harness: a `use <harness>_model, only: <names>` naming only the harness's distributed-state operations for a physics source (the grid queries, the halo exchange, the rank queries, the reductions) — `use mpi`, `use mpi_f08`, `include 'mpif.h'` and a call of or reference to any procedure whose name starts with `mpi_` are refused deterministically, and so is a harness `use` with no `only:` list or naming anything else (the partition, the writers, the capture operations, the gathers and the start and end of the runtime are the driver's). A value over the whole field that a `problem` forms itself goes through the harness reductions. Every cell of a case is held by the same number of ranks — all of them on a case too small to split, all those along the other dimension on a node with fewer axes than the grid has dimensions, one on a distributed block — and the kernel cannot tell how many without deciding from the grid, so a `<harness>__reduce_sum` over the ranks counts each cell once per rank holding it: an extreme goes through `<harness>__reduce_max` / `__reduce_min`, which a cell held on several ranks does not change; a mean is the `<harness>__reduce_sum` of the block's sum divided by the `<harness>__reduce_sum_int` of the block's cell count, the same cells counted the same number of times, so the quotient is the field's mean on every grid; a total is that mean times the case's cell count from a `derived` binding; and a reduced sum not divided by the reduced count of the cells it summed is as many times too large as ranks hold each cell, on a grid that holds a cell on several (a reduced count of refusals compared against zero tells whether any rank refuses). Every rank calls these in the same order: they are collective, and so are the halo exchange and the driver's gathers, so a refusal inside a step that precedes a collective is made the same on every rank by a reduction first (a rank that returns early past a collective stops every other rank there). Each of these harness operations is called from serial code, outside every threaded region of your source: the harness initializes the runtime so that only the thread that initialized it calls it, so on a target whose ranks also run threads a halo exchange or a reduction sits between threaded loops, never inside one. Declare `"state_residency": "distributed"` and `distributed_state@2` in `capability_requirements` on both kinds, with `"parallelization": {"model": "mpi", ...}`. The floor here is deterministic: on a `component` or `problem` node the `Generate.gate` static check FAILS a source that reaches the runtime directly, a component model source that names a harness operation, and a plan whose `state_residency` is not `distributed`. Satisfying it alone is not the bar: what this paragraph states beyond the floor is required as well.
