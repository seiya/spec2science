# Command-log & program-output placement

> **Audience: the conductor's deterministic Generate / Build / Validate.execute substeps, which call the build-runtime library (`docs/BUILD_RUNTIME.md`).**
> This is the canonical source for where the build-runtime side output `command_log.jsonl`, the
> host-authored build control file under `src/`, and the Validate.execute program output
> (`perf.json` / `raw/*`) must be placed in `allowed_output_paths`, and
> for the routing / forge-prevention rules the post_build / post_execute gates
> enforce. (The pipeline `lineage.json` is NOT a leaf output — the conductor authors it
> host-side; see below.) It lives under `docs/`, which the host reads when it assembles a prompt. The
> substep launch prompt carries a one-line pointer to this doc instead of inlining the full
> content (per-launch token-cost reduction). The conductor lists these paths when it builds a
> deterministic substep's request (`build_launch_request`); `record-launch` neither injects nor
> matches them (issue #643).

## Canonical `allowed_output_paths` placement of `command_log.jsonl`

- **Always include the build-runtime side output `command_log.jsonl` in `allowed_output_paths`.** The canonical placement per phase is the following:
  - Generate substep: `<pipeline_ref>/source/<source_id>/src/command_log.jsonl` (run_linter / run_syntax_check). **The `run_linter` / `run_syntax_check` side outputs are produced by the conductor's deterministic `generate.gate` substep (its lint and syntax checks)** (no LLM leaf runs either; `run_syntax_check` executes in a throwaway staging dir under `workspace/tmp/` but logs to this same canonical path). Because the `allowed_output_paths` of the `generate.verify` substep does not authorize the `run_linter` side output (`command_log.jsonl`), do not write `run_linter` execution in the verify launch prompt. `generate.verify` launches **no** validator gate: `post_generate` and `validate_workspace_root.py` moved to the conductor's deterministic `generate.gate` substep (its static check) (`generate.verify` maps to `(none)` in the "substep ↔ allowed validator gate correspondence table").
  - A `workshop leaf`'s wrapper ([issue #534](https://github.com/seiya/spec2science/issues/534); `tools/workshop_wrapper.py`): `workspace/orchestrations/<orchestration_id>/workshop/<lineage_id>/command_log.jsonl`, for every build-runtime call of the lineage and each `derive` and `check_ir`. No gate reads it as evidence: the gates run on the snapshot and write their own logs at the placements above.
- **The pipeline `lineage.json` is NOT a leaf output — do not list it in any `allowed_output_paths`.** It sits at the pipeline root. No leaf can write it — the host writes every artifact (since Z4, [issue #171](https://github.com/seiya/spec2science/issues/171)), and a `workshop leaf` cannot reach the checkout — a CLI leaf runs under an empty tmpfs at the checkout path, and an HTTP leaf's file tools resolve paths inside its work tree alone — and before that the root had to stay non-writable because the Edit/Write tools' atomic temp-sibling+rename would have needed the whole root writable. The conductor authors it host-side (`tools/workflow_conductor.py:_write_lineage`) before `Generate.verify` runs, per `docs/WORKSPACE_LAYOUT.md`. `Generate.verify` only **reads** it (it was in verify's `skill_must_read_refs`; that field is empty on every launch since Z4, and what a verify leaf is given is a `seed` file of its work tree, from its `pure_context`).
  - Build step (in-phase, CMake/Meson out-of-source): `<pipeline_ref>/binary/<binary_id>/command_log.jsonl` (compile_project, project_dir=<binary_id>/)
  - Build step (cross-phase, an in-source build — the build system's `control_file` declares `BUILDS_IN_SOURCE`; `make` does, [CONTROL_FILE.md](../backends/build_system/make/CONTROL_FILE.md) §1): `<pipeline_ref>/source/<source_id>/src/command_log.jsonl` (compile_project, project_dir=<source_id>/src/). An `oracle build` ([issue #680](https://github.com/seiya/spec2science/issues/680)) runs in a copy of `src/` under `workspace/tmp/<agent_run_id>/oracle/<build_id>/src/` and passes this same log as `command_log_path`. Bound by the `source_id` of the launch request, and `record-launch` verifies `verification_status=pass` of `source_meta.json`. At a remote `execution site` (issue #333) the build runs as a job there and the host writes the entry at this same placement, in the same shape plus a `site` object, with `command` the argv the local build-runtime call would have run (`CommandSpec.record_argv`) and `site.remote_command` the one the site ran
  - Validate.execute substep (in-phase): `<pipeline_ref>/runs/<run_id>/<node_key_safe>/command_log.jsonl` (run_program etc.)
  - Validate.execute substep (cross-phase quality_check): `<pipeline_ref>/source/<source_id>/src/command_log.jsonl` (`phase_04_validate.md` — with an in-source build system (`BUILDS_IN_SOURCE`) and a compiled `toolchain.language`, `run_quality_checks` runs with `project_dir=source/<source_id>/src/`, so the log is side-output into the generate tree). When `source_id` is included in the launch request of the Validate.execute substep, the runtime derives the cross-phase canonical placement from it. `source_id` is verified by the existence of `<pipeline_ref>/source/<source_id>/source_meta.json`, and passing an unknown source_id (a value not corresponding to an actual generate execution) makes `record-launch` reject with a `ValueError` (prevention of cross-phase write authorization injection by an arbitrary caller).

  `trial_meta.json#source_command_ref.run_quality_checks.command_log_ref` names `<pipeline_ref>/source/<source_source_id>/src/command_log.jsonl`, the log of the trial's own source: the conductor writes the entry, and no gate re-checks its placement since [issue #674](https://github.com/seiya/spec2science/issues/674) (the post_execute validator refused a sibling generation's log until then).

  The cross-phase canonical placement of the Validate.execute substep is bound only to the `source_id` field of the launch request. A path listed under `<pipeline_ref>/source/<other_source_id>/src/...` (a generation different from the request's `source_id`) authorizes nothing: the placement is derived from `source_id`, not from the list. On the trial_meta side too, `source_source_id` is a required record, fixing the bind between execute and generate.

  **Single-namespace enforcement:** the `allowed_output_paths` of a generate / build / validate step (Validate.execute substep) must target only a single `<source_id>` / `<binary_id>` / `<run_id>`. Mixing and listing multiple ids under the same pipeline makes `record-launch` reject with a `ValueError` (prevention of granting write authority to the audit log of a sibling/older run). For Generate / Validate.execute, it additionally requires that the request's `source_id` / `run_id` matches the ids of the listed paths (a mismatch is rejected with `does not match request ...id`).

  **Canonical form of `run_id` (Validate):** `run_id` is the only one in the id family with a **fixed literal `run_` prefix**, in the form `run_<YYYYMMDD>_<seq3>` (e.g. `run_20260605_001`). The `<slug>_<YYYYMMDD>_<seq3>` form of `ir_id` / `pipeline_id` (slug being hyphen-separated) **must not be reused** — for example `run-rsn-p0_20260605_001` matches the slug form (slug=`run-rsn-p0`) but is not a canonical `run_id`: the run discovery of Validate `post_execute` recognizes only the literal `run_` layout and fails with `no execution artifacts found`. The conductor mints every `run_id` in the canonical form; `record-launch` does not re-check it (issue #643). Good example `run_20260605_001` ✓ / bad example `run-rsn-p0_20260605_001` ✗.

  **Quality_check stale-generation countermeasure:** `record-launch` checks `verification_status` and rejects, at launch time, granting write authority to the build-runtime audit log under a failed generation (prevention of provenance contamination of a failed gen tree).

  **Build lineage bind (specific build):** the launch request of the Validate.execute substep requires recording `source_binary_id`, and the `source_source_id` of `<pipeline>/binary/<source_binary_id>/binary_meta.json` must match the request's `source_id`. A missing `source_binary_id`, an absent binary_meta.json, an unrecorded `source_source_id`, or a value mismatch is rejected by record_launch. This prevents a mixed-build forge (reusing the quality_check evidence of build B while running the binary of build A). The Build step records `source_source_id` in `binary_meta.json` as required (see `phase_03_build.md`).

  **In-source-only gate of the cross-phase placement:** the cross-phase placement `<pipeline>/source/<source_id>/src/command_log.jsonl` exists only when the target's build system builds in source — its `control_file` backend declares `BUILDS_IN_SOURCE` (`orchestration_runtime._builds_in_source`; `make` does). For an out-of-source build system there is no cross-phase placement, and the build/execute log has only the in-phase canonical (`binary/<binary_id>/command_log.jsonl` or `runs/<run_id>/<node_key_safe>/command_log.jsonl`). `record-launch` reads `toolchain.build_system` of the target profile the request's `pipeline_ref` names (`spec/targets/<target_id>.yaml`, issue #284) and judges automatically.

  **Out-of-source dir override of an in-source build (`BUILDS_IN_SOURCE`):** an in-source build's `compile_project`/`run_quality_checks` runs with `project_dir=<pipeline>/source/<source_id>/src/`, but emitting build artifacts into `src/` would contaminate the certified source tree with build output. Because the control file under `src/` already declares overridable object, binary and run-output directories, pass an absolute-path override of each at launch to route artifacts out of `src/`. [CONTROL_FILE.md](../backends/build_system/make/CONTROL_FILE.md) §1 states the `make` variables and the exact `extra_args` / `env` values:
  - **Build step:** `compile_project` overrides the object directory to `<repo_abs>/workspace/tmp/<build_agent_run_id>/build` and the binary directory to `<repo_abs>/<pipeline_ref>/binary/<binary_id>/bin`. Objects and module artifacts land in a per-run tmp (`workspace/tmp/<agent_run_id>/` — auto-authorize + auto-clean on success), and the execution binary lands in `binary/<binary_id>/bin/`. Include the execution binary `<pipeline_ref>/binary/<binary_id>/bin/<exe>` in `allowed_output_paths` in **file form**. The `allowed_file_tool_paths` half of this rule described a leaf's `Edit` / `Write` eligibility and is deleted with it ([issue #171](https://github.com/seiya/spec2science/issues/171) PR-2). `binary_meta.json#binary_artifact_ref` points to `binary/<binary_id>/bin/<exe>`.
  - **Validate.execute substep:** `run_quality_checks` passes, through `env`, the object directory `<repo_abs>/workspace/tmp/<exec_agent_run_id>/build`, the binary directory `<repo_abs>/<pipeline_ref>/binary/<source_binary_id>/bin`, the run-output directory `<repo_abs>/workspace/tmp/<exec_agent_run_id>/qc_run`, the binary name `<spec_id>_runner`, the IR `<repo_abs>/<ir_ref>/spec.ir.yaml` and the case list (`run_quality_checks` is a fixed command but propagates `env` to the build tool; the IR and the case list make the quality-check target invoke the runner with the same argv `run_program` uses, so the quality-check re-run's host verdict is comparable for the `quality_check` comparison). The quality-check target does not relink (it references the existing binary via the control file's fail-closed guard), and the `perf.json` / `raw/*` emitted by the quality-check binary re-run are confined under tmp (`workspace/tmp/<exec_agent_run_id>/qc_run`, a separate subdir from `run_program`'s `run/`). Pointing the run-output directory at the canonical run node dir would have the quality-check binary's writes clobber the agent-promoted `run_program` copy with provenance-mismatched output, so always point it at tmp (for details see "Validate.execute program output routing — direct binary write forbidden" below). All canonical `.json` is re-authored after both `run_program` and `run_quality_checks` complete (the final step) — by the conductor's own `Validate.execute` body, which is a deterministic in-process substep. The only write to `src/` is the cross-phase audit log.

  **A quality check that did not exit 0:** the conductor fails the quality check when the `run_quality_checks` re-run is not `ok` (`Conductor._author_quality_check`, [issue #674](https://github.com/seiya/spec2science/issues/674)), and a failed `run_program` writes no `trial_meta.json`: the conductor stops the run first. No gate reads the record's `ok` (the post_execute validator did until issue #674).

  **Role binding for source_command_ref:** `Conductor._execute_inproc` writes the Validate.execute `trial_meta.json`'s `source_command_ref` itself, one `run_program` and one `run_quality_checks` entry, each with its `tool_name`, `command_id` and `command_log_ref` taken from the record the build-runtime library returned. No gate re-checks the role binding since [issue #643](https://github.com/seiya/spec2science/issues/643) PR-4 (the tool_name, the `compile_project` exclusion and the required `run_program` entry were `_validate_trial_meta`'s; the host is the only writer). The post_execute validator read the `run_quality_checks` entry until [issue #674](https://github.com/seiya/spec2science/issues/674); it reads neither entry now.

  **Run_program log canonical placement:** the log belongs at `<pipeline_ref>/runs/<run_id>/<node_key_safe>/command_log.jsonl`. Set `project_dir` to the execute node dir, or name the path explicitly with `command_log_path`. The conductor places it there (`Conductor._execute_inproc`); no gate re-checks the placement ([issue #643](https://github.com/seiya/spec2science/issues/643)). A pre-call gate in the build-runtime layer (`validate_mcp_build_tool_invocation`, then an MCP server; the protocol layer was deleted in [issue #444](https://github.com/seiya/spec2science/issues/444)) rejected a non-canonical placement at call time until [issue #171](https://github.com/seiya/spec2science/issues/171) PR-2; it existed because the CALLER might be a leaf, and the caller is the conductor. At a remote `execution site` ([issue #293](https://github.com/seiya/spec2science/issues/293)) the library does not run the command: the host writes the entry after collecting the job, through the same `_append_command_log`, at the same placement and in the same shape plus a `site` object — `cwd` and `command` name the local directory and the local files the command stands for, and `site.remote_cwd` / `site.remote_command` what the site executed (`docs/ORCHESTRATION.md` §Execution sites).

  **Validate.execute program output (`perf.json`/`raw/*`) routing — direct binary write forbidden:** `command_log.jsonl` is a **build-runtime-owned audit log** for which a canonical direct write is permitted (the trust model above). On the other hand, `perf.json` / `raw/*` are the **program output of the binary (runner)** that `run_program` runs, and the canonical copy must be the agent-authored evidence with correct `run_program` provenance — not whatever the binary happened to drop. Having the binary write directly to the canonical run dir (`<pipeline_ref>/runs/<run_id>/<node_key_safe>/`) lets the later `run_quality_checks` make-test re-run clobber the `run_program` evidence and mixes `run/` vs `qc_run/` provenance. The launch specifies the following routing:
  - **Point the binary output destination at tmp:** make `run_program`'s `project_dir` (= the binary's cwd) or the case's output destination `allowed_tmp_root` (`workspace/tmp/<exec_agent_run_id>/run/`), and have the binary drop `perf.json` / raw / logs to **tmp (auto-authorize)**. **`run_quality_checks` (`make test`) likewise**: point `env.RUNDIR` at `workspace/tmp/<exec_agent_run_id>/qc_run` (a separate subdir from run_program's `run/`), and confine the `perf.json` / `raw/*` emitted by the `make test` binary re-run to tmp too. Pointing `RUNDIR` at the canonical run node dir would have the `make test` direct binary write clobber the agent-authored copy already re-authored after `run_program` and produce a provenance mismatch (a typical ordering defect).
  - **Make command_log_path canonical explicit:** because making `project_dir` tmp would drop the command log into tmp too, make `<repo_abs>/<pipeline_ref>/runs/<run_id>/<node_key_safe>/command_log.jsonl` explicit with the `command_log_path` argument to satisfy the "Run_program log canonical placement" gate above.
  - **The agent re-authors the canonical `.json` (final step):** the execute body reads the `perf.json` / `raw/*` of the **`run/` tmp tree** (`workspace/tmp/<exec_agent_run_id>/run/`, = the output of the `run_program` execution with `spec.ir.yaml.case` as arguments), and re-authors the canonical `runs/<run_id>/<node_key_safe>/perf.json` / `raw/state_snapshots/*` itself. **The runner's program output (`perf.json` / `raw/state_snapshots/*`) is always promoted from `run/`, and must not be promoted from `qc_run/` (the output of the make-test re-run)** — if `qc_run/` is promoted, the canonical evidence does not correspond to the required `run_program` invocation (the `spec.ir.yaml.case` and its `command_log`), and the verdict is evaluated over evidence with a provenance mismatch. The output of `qc_run/` is referenced only for the quality-check comparison (the verdict computation of `quality_check.json`). `trial_meta.json` and `quality_check.json` are **not runner output but metadata the host authors** (`trial_meta.json` is composed from the build-runtime command refs / `source_source_id` / `source_command_ref`, and `quality_check.json` from the comparison result. The runner must not output either file directly), and are written directly rather than promoted from tmp. **The re-author is the final step after both `run_program` and `run_quality_checks` complete**, ensuring an order in which a subsequent binary re-run does not overwrite the agent-authored copy (the ordering of authoring after run_program then running make test in the canonical RUNDIR is an overwrite defect).
  - **raw `.json`, non-`.json` and the logs are re-authored the same way** — the `.json` under `raw/` (`state_snapshots/*.json`), the non-`.json` files under `raw/`, `stdout.log` and `stderr.log`. (The `Write`-tool / `allowed_file_tool_paths` protocol this bullet stated was the agentic leaf's and is deleted with it.)

  **Build-runtime audit log trust model — what it rests on NOW.** `validate_pipeline_semantics.py` reads these logs and trusts their records (`tool_name`, `ok`, `command`) as evidence that a tool actually ran, so the question is who can write one. Until Z4 ([issue #171](https://github.com/seiya/spec2science/issues/171)) the answer was a stack of hook policies refusing every other route from a leaf that held `Edit` / `Write` and a shell. **No leaf holds any of them now**, and a leaf's sandbox does not hold the checkout at all (an empty tmpfs at `repo_root`, [issue #227](https://github.com/seiya/spec2science/issues/227), and one at the framework root when it is another directory, [issue #705](https://github.com/seiya/spec2science/issues/705)), so the only writer that can reach the path is the build-runtime library, called in the conductor's own process. That is a structural closure rather than a pattern-matching one — but it is still not a cryptographic proof: a defect in the HOST could write a record no tool produced, and the library keeps no signed ledger the validator could cross-reference. That extension stays future work.

  **Host-authored build control file under `src/`:** for a node whose target's build system and language both declare `control_file` (leaf **or** with dependencies) the conductor authors the control file under `src/` host-side; [CONTROL_FILE.md](../backends/build_system/make/CONTROL_FILE.md) §1 states the `make` binding and the languages that declare it. A `record-launch` auto-inject of that path into a leaf's `allowed_output_paths` / `allowed_file_tool_paths` covered the languages the host did not author for, where the extension-less name fell outside the directory allowlist's source-extension set; it is deleted with the leaf's write authority ([issue #171](https://github.com/seiya/spec2science/issues/171) PR-2).

  A DETERMINISTIC substep's declared outputs are the list the conductor builds (`build_launch_request`); `record-launch` no longer injects the canonical log placements into it or matches it against the phase contract (issue #643), and `determine_substep_status` reads the conductor's list, skipping the audit logs. That declaration is not an authority: nothing enforces it against the conductor's own process. The list of write paths this bullet used to enumerate as REFUSED — the `Edit` / `Write` tools, Bash redirects, `tee`, `sed -i`, `cp` / `mv` / `install` / `ln` / `touch` / `truncate` / `dd` — was refused by hook policies over a leaf that held those tools over the checkout, and none of them reaches the checkout now: a `workshop leaf` cannot reach the checkout — a CLI leaf runs under an empty tmpfs at the checkout path, and an HTTP leaf's file tools resolve paths inside its work tree alone.
