# Phase 4: Validate

## Overview
The phase that runs the binary produced by `Build`, obtains the primary evidence, and finalizes the pass/fail judgment. It is defined as a single phase with the 2 substeps `execute` (execution, primary-evidence collection and the host-authored per-test verdict) and `post_judge` (the derived artifacts, the deterministic `--stage pre_judge` gate and its severity classification). Both are conductor-in-process deterministic substeps, mirroring the `Compile.static` / `Generate.gate` deterministic-gate hoists; no LLM leaf runs in this phase.

## I/O contract
- execution input: `binary/<binary_id>/bin/`, `spec.ir.yaml`, `tests.md`
- verification input: `spec.ir.yaml`, `source/<source_id>/`, the `raw/` / `perf.json` / `quality_check.json` / `trial_meta.json` under the same `run_id`. `Validate.execute` resolves `<source_id>` from the launch request, which records it as required (runtime-enforced; its match with `binary_meta.json.source_source_id` is also verified).
- no other target's run: since [issue #383](https://github.com/seiya/spec2science/issues/383) a node whose IR has a cross-target primary predicate is compared with the other declared targets' runs by the `cross-target agreement`, which the host evaluates beside the certification and outside this phase (`docs/ORCHESTRATION.md` 13d). No substep of this phase reads another target's run.
- output: the following under `workspace/pipelines/<node_key_safe>/<target_id>/<pipeline_id>/runs/<run_id>/<node_key_safe>/`:
  - `perf.json`, `quality_check.json`, `raw/`, `stdout.log`, `stderr.log`, `verdict.json` (execute substep — `verdict.json` is host-authored deterministically from `io_contract.tests` + `io_contract.predicates` over the captures, R2)
  - `aggregate_verdict.json`, `summary.json`, `validate_meta.json`, `post_judge_meta.json` (post_judge substep — the first three conductor-derived from `verdict.json#per_test` + the dependency set, G6)
  - the `command_id` and `command_log_ref` of `run_program`

## substep structure
- **Dependency-DAG readiness** runs in the conductor before any substep of the phase (`run_phase`): a not-built+validated `dependency_graph.json` sidecar `all_nodes` closure fails the phase `fail_closed` (`validate_pre_judge_dag_incomplete`, event `judge_pre_spawn_blocked`; a non-physics integrity blocker) before `execute` is reached. A single-node run (empty closure) passes with zero overhead. §4-3 states the check.
- `Validate.execute`: a **non-LLM substep** that runs the binary through the build-runtime library and generates the primary evidence (`raw/` / `perf.json` / `quality_check.json` / `stdout.log` / `stderr.log`), then **authors `verdict.json` deterministically** (R2) by evaluating `io_contract.predicates` against the captures under `raw/state_snapshots/` (Z6, [issue #255](https://github.com/seiya/spec2science/issues/255); `tools/primary_evidence.py`) (per-test `status` + `failure_class`). A predicate `fail` (`self_verdict=fail`) fails the execute substep, so `post_judge` is not reached, and the failure routes via `classify_failure` on `verdict.json#failure_class`.
- `Validate.post_judge`: a **non-LLM substep** (conductor in-process, `_post_judge_inproc`) that FIRST authors the deterministically-derivable `aggregate_verdict.json` / `summary.json` / `validate_meta.json` from the execute-authored `verdict.json#per_test` + the dependency set (G6, correct-by-construction), then runs the `--stage pre_judge` gate and classifies the violation severity into `post_judge_meta.json` (`disposition`). §4-3 states the classes and what each does; `docs/design/deterministic_followups.md` §G4/G5 is the design record.
- **Names kept from the deleted judge.** The phase had an LLM `judge` substep and a `pre_judge` substep before [issue #724](https://github.com/seiya/spec2science/issues/724); both are deleted, and no `pre_judge_meta.json` or `semantic_review.json` is written. The names below are kept because they are persisted in every record: the validator STAGE `pre_judge` (`--stage pre_judge`, recorded as `validation_stage: "pre_judge"`) is the certification gate `post_judge` runs — "before pass-certification", not a substep; `validate_pre_judge_dag_incomplete` and `judge_pre_spawn_blocked` are the reason and the event of the DAG check above; `pre_judge_violation` is the `failure_category` of a `post_judge` gate `fail`; `post_judge` and `post_judge_meta.json` name the substep and its record.
- **Terminal reason of a failed `post_judge`**: derived from that substep's own `post_judge_meta.json` by `classify_validate_gate_failure`. A record that names no `failure_category` is reported under a reason that names no violation. `docs/RUNBOOK.md` §3-1 is canonical for the reason set and the operator procedure.

## `run_id` format
- Format: `run_<YYYYMMDD>_<seq3>`, e.g. `run_20260511_001`
- `run_id` has a fixed literal `run_` prefix. The `ir_id` / `pipeline_id` form `<slug>_<YYYYMMDD>_<seq3>` (slug being hyphen-separated) must not be reused. A hyphen-slug form such as `run-rsn-p0_20260605_001` matches the generic slug grammar but is not a canonical `run_id`: the run discovery of `post_execute` recognizes only the literal `run_` layout and would fail with `no execution artifacts found`. The conductor mints every `run_id` in the canonical form; `record-launch` does not re-check it (issue #643).

## `validate_meta.json` required keys
- Common: `attempt_count`, `verification_status`, `last_fail_reason`, `debug_mode`, `context_isolated`
  - `attempt_count` is `1`: a run node directory belongs to one attempt of the phase, and a phase retry rotates `run_id` into a fresh directory.
  - `last_fail_reason` is **`None` in every run today**, and that is a consequence of issue #176 rather than a defect: the conductor fills it from a PRIOR `post_judge_meta.json` in the same run-node directory, the deleted warm-resume mini-loop was the only thing that ever wrote a second one there, and a phase retry rotates `run_id` into a fresh directory. The key stays required and the read stays, defensively; nothing fills it.
- When `context_isolated=false`, `constraint_reason` is required.
- `artifact_hashes`, `output_hash`, `derivation_key`, `derivation_inputs`, `derivation_transformation`: stamped by the host at `write-step-result` on a `pass` ([issue #250](https://github.com/seiya/spec2science/issues/250) PR-1 — `validate_meta.json` is Validate's certifying meta, like the other three phases'). `artifact_hashes` pins the three other declared deliverables of the run node directory (`aggregate_verdict.json`, `verdict.json`, `summary.json`). `check-phase-certified` reads Validate through this stamp since PR-2 of that issue (status + hashes + key), like every other phase: a run directory that died before `write-step-result` carries no stamp and is not certified.
- `trial_meta.json#environment.platform` (`machine`, `node`, `cpu_model`, `gpu`, `site`): the host the evidence was produced on and the `execution site` — recorded by `Validate.execute`, not part of any derivation key (issue #250; `site`, issue #289; `gpu`, the first line of the device probe the hardware class names, issue #293). A remote site's values are its own answers.
- `trial_meta.json#environment.execution_site` (`site`, `host`, `scheduler`, `job_id`, `remote_dir`, `queue_wait_ms`): how the site was reached (issue #293; `docs/ORCHESTRATION.md` §Execution sites) — `host` and `remote_dir` are null at `local`. A record, not a key input.
- `trial_meta.json#environment.launch` (`argv_prefix`, `env`): the `launch shape` the binary ran with, as `tools/host_execution.py` composed it from the target profile (issue #289); `env` is the override set, not the whole environment: at `local` `run_program` merges it over the host process's own environment, and at a remote site the job script sets it over the site's non-interactive login environment after the site's `setup` lines (issue #293). Either is handed exactly this `env` and command; `run_program` no longer takes a hardware class or a thread count. A parallel backend that declares `device_trace` (`cuda`) puts its device trace in `argv_prefix` (issue #307), one that declares `launcher` (`mpi`) puts its launcher there with the profile's `execution.ranks`, outermost (issue #316; `docs/backends/parallel/mpi/LAUNCHER.md`). `trial_meta.json#environment.ranks` records the rank count. Under a launcher the quality check (`Conductor._author_quality_check`) requires `perf.json#parallelism.mpi_ranks` to equal it and `perf.json#parallelism.process_grid` to be the grid the profile imposes (`execution.process_grid`, whose launch environment the backend composes; `[ranks, 1]` when it imposes none — issue #512), and fails the run otherwise. `trial_meta.json#environment.sweep` records the launch of each further execution shape (`execution.sweep`, issue #512; §4-2), and `environment.serial_reference_env` the environment of the quality check's serial reference. `environment.library_dirs` (issue #644) records the library directories of the `external library`s the closure declares, read from the Build's `binary_meta.json#library_dirs` (`[]` when it declares none): every run of the binary — the certified run, each sweep shape, the checked run and the quality check — is given the loader variable the target compiler's `library_binary` names, its value these directories prefixed to the value the run would otherwise inherit. Neither `launch.env` nor `serial_reference_env` holds that variable, and the joined value is not recorded (`docs/ORCHESTRATION.md` §Execution sites).
- `trial_meta.json#kernel_trace` (`artifact`, `command_id`, `command_log_ref`): present when the binary ran under a device trace (issue #307) — the promoted per-kernel summary (`kernel_trace.csv`) and the `run_program` log entry of the command that wrote it. Kept apart from `source_command_ref`, whose `run_program` entry is the binary's run. A record, not a key input.
- `trial_meta.json#test_profile_id` / `test_profile_version`: the test profile the cases were authored under — the value every case of `spec.ir.yaml` declares under `inputs`, `null` when a case lacks it or two cases disagree — recorded by `Validate.execute` because every `tests.md` §8 asks for it in this file, which only the host writes (issue #346). A record, not a key input: no gate and no verdict predicate reads it.

## substep details

### 4-1. Validate.execute substep
> **Runner program-output contract** (what `perf.json` / `raw/` must contain + the JSON serialization rules, whose per-language binding is `docs/backends/language/<language>/RUNNER_OUTPUT.md`) is canonical in [docs/workflow/RUNNER_OUTPUT_CONTRACT.md](../RUNNER_OUTPUT_CONTRACT.md). `Validate.execute` is run in-process by the conductor (no LLM leaf) and follows the placement/provenance rules below.
- `Validate.execute` does not involve standard LLM inference, and limits its responsibility to writing the case files (`RUNNER_OUTPUT_CONTRACT.md` §6; a remote job ships them), the build-runtime `run_program` call and recording the result. On an M3c node the binary is the host-rendered driver over the certified harness and the leaf's model ([RUNNER_OUTPUT_CONTRACT.md](../RUNNER_OUTPUT_CONTRACT.md) §3).
- **The second pass** ([issue #632](https://github.com/seiya/spec2science/issues/632)). A `continuation case` (`docs/GLOSSARY.md` §4; `phase_01_compile.md`, the `case` block) is not run with the others. Each execution shape — the run, the quality check's re-run, each sweep shape, the checked binary — first runs the base cases. Then, for every continuation, the host writes its case file from that shape's OWN restart point of its base at its restart step `K`, with a copy of the IR, under the shape's `restart/` directory (`primary_evidence.write_continuation_inputs`), and runs it in a process of its own: the same binary, launch shape and environment, `--cases <shape>/restart/spec.ir.yaml <case_id>` with its working directory there (the quality check's re-run: that one case and that run directory). The driver reads `restart.step` = `K` after `init`, overwrites each restart variable from `restart.<v>`, and starts `step` at `K` and `t` at `t_start + K * dt`, so its initial capture holds the restart point's values, its samples and restart points are those above `K` and its series runs over `K + 1 .. n_step`; a value outside `0 .. n_step - 1` on a case `init` did not refuse stops it before a capture. Before its captures count the host checks that its initial capture carries `step` = `K`, the restart point's time and every restart variable's value there (`continuation_start_violation`), then moves them into the shape's own capture directory; its `perf.json` stays under `restart/` and is no performance record. At a remote site the second pass is a second job, in a job directory of its own, after the first job's directories came home, and a different machine fails the run. `trial_meta.json#runner_command` names the first invocation's cases; `trial_meta.json#restart_pass` records, per shape, each continuation's `command_id` (its command is that entry of the run's `command_log.jsonl`, or, for the quality check's re-run, of the source's) and whether it started at its restart point, and the host refuses the captures of one that did not. A continuation with no captures in a shape fails the run, and the failure names the continuation, the shape and the cause (`[execute fail: continuation]`): in the run's own shape as a missing deliverable, in another as that shape's disagreement with the serial reference. A second-pass process that does not exit 0 fails the run as a runtime failure of the binary (`[run_program failed: runtime_error]`, naming the continuation) when it ran in the run's own shape or the quality check's re-run, and fails its row of `quality_check.json` when it ran in a sweep shape or the checked binary. `--resume` re-runs the attempt from the first pass.
- Always include `spec.ir.yaml.case` in the `run_program` execution command (as the determined values of runtime input).
- The command and the environment `run_program` is given are the target's `launch shape` (`tools/host_execution.py`, issue #289). A target whose hardware class no reachable site executes never reaches this substep: the launch gate refuses it — the registry half for a run that reaches `Validate`, the site half already for one that reaches `Build` (`target_profile.target_profile_violations` for the registry half, `execution_sites.site_violations` for the site half), and the seam refuses it again here as a transport `fail_closed` if the gate was bypassed.
- When the target's parallel backend declares `device_trace` (`cuda`; issue #307, `docs/backends/parallel/cuda/DEVICE_TRACE.md`), the binary runs under the trace's prefix and a third command — the trace's summary, logged as a `run_program` entry in the same `command_log.jsonl` — runs in the run's working directory between the run and the quality check, only after a run that exited 0. Its file is promoted to the run node as `kernel_trace.csv`, a deliverable of the substep for such a target. A summary command that fails, or exits 0 without writing its file, is a transport `fail_closed` (`deterministic_validate_error`): host tooling, not the kernel. The quality check is not traced. The `post_execute` gate then reads the summary (`_validate_device_kernel_execution`): every kernel the node's own sources define (every source under its `src/`; a dependency's are not there) must have at least one instance in it. A summary that records NO kernel while the sources define some fails the run with exit code 6 (`device_kernels_absent`, terminal, below); some defined kernels without an instance is an ordinary violation (`post_execute_violation`). A node whose sources define no kernel is asked nothing. The summary counts only when `trial_meta.json#kernel_trace` names a successful `run_program` record of the target's summary command in this node's `command_log.jsonl`.
- At a remote `execution site` the same commands run as one job there (`tools/remote_execution.py`, issue #293), and each `command_log.jsonl` entry is written by the host, at the same placement, in the same shape plus a `site` object; a failure to reach the site or to collect the evidence is a transport `fail_closed` (`deterministic_validate_error`), never the kernel's. A binary runs only at the site that built it (issue #333), at a remote site and at `local` alike: before anything runs, `binary_meta.json#environment.build_site` must name the site this run is at — its id and its `host` — or the substep is the same transport `fail_closed` (a record naming no build site included); at a remote site the job also refuses a machine whose `uname -m` is not `environment.platform.machine`, the architecture that built the binary (a record naming none is refused before the site is contacted). `docs/ORCHESTRATION.md` §Execution sites is canonical.
- Save the actual-command record of `run_program` in `JSONL` format, with the default destination `project_dir/command_log.jsonl`.
- `Validate.execute` runs individually per `node`, and must not mix in the artifacts of other `node`.
- The output targets of the `runner` are limited to `perf.json`, the `raw/state_snapshots/` captures, `stdout.log`, and `stderr.log`.
- The `runner` (the binary that `run_program` runs) **must not write `perf.json` or a capture directly** to the canonical run dir. The canonical copy must be the agent-authored evidence with correct `run_program` provenance — not whatever the binary happened to drop — and letting the binary write the canonical dir lets the later `run_quality_checks` make-test re-run clobber it. Drop the binary's output to `allowed_tmp_root` (`workspace/tmp/<exec_agent_run_id>/`), and the `Validate.execute` agent reads the `.json` of the `run/` tmp tree (`workspace/tmp/<exec_agent_run_id>/run/`, = the output of the `run_program` execution) and re-authors the canonical `perf.json` and `raw/state_snapshots/*` with the `Write` tool. The runner's program output (`perf.json` / `raw/state_snapshots/*`) is always promoted from `run/`, and must not be promoted from `qc_run/` (the output of the `run_quality_checks` / make-test re-run) (if promoted, the verdict would be evaluated over evidence with a provenance mismatch). `qc_run/` is referenced only for the quality-check comparison (`quality_check.json`). `trial_meta.json` and `quality_check.json` are not runner output but metadata the agent authors (the runner must not output them directly), and are written with the `Write` tool rather than promoted from tmp. `Validate.execute` is a DETERMINISTIC substep in the conductor's own process, so it writes all of these directly; the `Write`-tool / `write_roots`-containment protocol this paragraph stated was the agentic leaf's and went with it (Z4, [issue #171](https://github.com/seiya/spec2science/issues/171)).
- The `runner` must not write `verdict.json`, `aggregate_verdict.json`, `summary.json`, or `trial_meta.json`. `verdict.json` is host-authored by the conductor in `Validate.execute` (R2, from `io_contract.tests` + `io_contract.predicates` over the captures); `aggregate_verdict.json` / `summary.json` are conductor-derived in `Validate.post_judge` (G6). The runner emits only `perf.json` and `raw/state_snapshots/*`; the per-test verdict is computed FROM the captures, never BY the runner.
- **`Validate.execute` authors `verdict.json` (R2; [issue #582](https://github.com/seiya/spec2science/issues/582)).** After the primary evidence is promoted and the `post_execute` structural gate + `quality_check` pass (a structurally-invalid run authors NO verdict and routes to `Generate`), the conductor evaluates `io_contract.predicates` against the promoted `initial` and `final` records of each case (`primary_evidence.evaluate_primary_predicates`, Z6, [issue #255](https://github.com/seiya/spec2science/issues/255)), folds the records by `io_contract.tests` (`verdict_evaluator.evaluate_verdict`), and writes `verdict.json` = `{node_key, run_id, self_verdict, failure_class, per_test:[{test_id, status, basis}], ir_hash}` (`ir_hash`: the output hash of the IR the validate key bound, which another target's comparand selection reads to tell whether this run was judged over the same IR). `status ∈ pass/xfail/fail`: a test's `status` is its `expected_outcome` when every record of the test that is not cross-target is satisfied, else `fail`. `basis` = `{predicates: [records]}`, one record per predicate of the test: `quantity`, `expr`, `op`, `scope`, `target_cases`, `cases_read` (the cases whose captured state enters the expression's value — `primary_evidence.cases_read`, [issue #567](https://github.com/seiya/spec2science/issues/567): every case the scope evaluates when the expression reads its own case's state, plus every case an `at('<case>').initial.<var>` / `at('<case>').final.<var>` state read names, counting only reads in `expr` or a bind `expr` reaches and outside a term constant by form), `sources_read` (the same reads per `source` class of `phase_01_compile.md`, `{source: [cases]}`), `grammar_version`, `satisfied`, `kind`, and per evaluated case the host-computed `value` against `rhs`, or an `evaluation_error`. A record that reads a `source: reported` variable with no record of the same quantity, not cross-target, reading `source: operation` state and no reported variable in those cases raises `PredicateError`: the Compile gate's rule, re-checked on the records. `failure_class = pass` (all predicates hold) / `physics_fail` (a comparison was false) / `structural_violation` (an expression could not be evaluated from the captures: a capture absent, ragged, non-finite or of the wrong rank (an empty array in a capture the host-rendered driver wrote, or of a variable of the `zero_extent:` line, is not asked its rank), a variable the case's capture does not hold, an `initial.<var>` of a case whose own runner commits no `initial` record, an array result, a non-integer shift — a contract or evidence gap). `self_verdict = fail` fails the execute substep. A cross-target predicate (grammar 3, `comparand.initial.<var>` / `comparand.final.<var>`, [issue #324](https://github.com/seiya/spec2science/issues/324)) is not evaluated in the verdict ([issue #383](https://github.com/seiya/spec2science/issues/383)): its record is `kind: no_comparand`, satisfied, with no comparand and nothing evaluated, on every run. `evaluate_verdict` refuses a cross-target record carrying a comparand or an evaluation (`PredicateError`, a `structural_violation` verdict) rather than ignore it. The comparison is the `cross-target agreement` (`docs/ORCHESTRATION.md` 13d; `docs/RUNBOOK.md` §3-0, certifying one node on several targets). This is a pure function of the IR + this run's captures. `summary.json` (G6) and the `--stage pre_judge` gate read `per_test[].status` only, and so does `aggregate_verdict.json`'s verdict; `basis` changes none of them.
- **The oracle** ([issue #680](https://github.com/seiya/spec2science/issues/680)). When the `node` declares an `oracle` for the target's language (`docs/SPEC.md` requirement 17), `Validate.execute` runs it after the verdict is evaluated and before it is written, only when the evaluated `self_verdict` is `pass` or `xfail`: a run that fails its own tests is routed by them, and the oracle does not run. Each `oracle build` runs the compared cases its declaration assigns it (`tools/oracle.py` `case_plan`: the cases the IR's cross-target predicates compare a comparand in that are not continuation cases) as the serial reference runs — bare, one process, one thread, under the serial reference's environment, at the `local` site — from `binary/<binary_id>/bin_oracle/<build_id>/<exe>`, with the loader path over the closure's library directories and then the build's own, in a directory of its own under `workspace/tmp/<agent_run_id>/oracle_run/`; its `run_program` record is in the run's `command_log.jsonl`. Its captures are moved into one directory (`move_case` of the target's capture store), and the IR's cross-target predicates compare them with the serial reference's (`qc_run/`), through the comparison the quality check applies to each execution shape (§4-2, "The implementation-quality judgment"), in every compared case: every cross-target predicate in each of those cases its scope holds. The oracle runs no second pass, so a continuation case is not compared ([issue #709](https://github.com/seiya/spec2science/issues/709)): the run's restart test, which runs before the oracle and must pass, already holds the continuation's final state equal to its base's, and the base is compared. The outcome, by the comparison's status:
  - `agree`: `verdict.json` is written and the substep goes on.
  - `disagree`: no `verdict.json` is written; `trial_meta.json` records `status: fail` and `failure_category: oracle_disagreement` (terminal, below), and its `failure_excerpt` names each failed comparison.
  - `unevaluable` (a capture absent or unreadable, or no compared case: every case under a cross-target predicate is a continuation case), or `not_applicable` (the IR holds no cross-target predicate, so nothing would be compared): a transport `fail_closed`, `oracle_unevaluable`. So `agree` means that every cross-target predicate was evaluated against the oracle in every compared case of its scope.
  - The other two transport `fail_closed` reasons: `oracle_run_failed`, an oracle run that did not exit 0 (the adapter's or the declaration's defect, not the generated model's), and `oracle_declaration_invalid`, a case plan the declaration breaks (a named case the IR does not hold, a case named twice, a compared case no build takes). Each message ends with its reason and remedy, which the run's failure summary keeps.

  On `agree` and on `disagree` the run node directory gains `oracle_check.json`: `status`, `node_key`, `run_id`, `declaration_sha256`, `source_sha256`, `origin`, `command_log_ref`, per build its `id`, `binary_ref`, `cases` and `command_id` (`null` for a build that ran no case), and `comparison` (`records_count`, and `failures` and `worst`, at most five each). It is listed in the launch's `allowed_output_paths` of a node that declares an oracle, and not in the step result's `required_outputs`: a record, like `quality_check.json`, which no certified artifact hashes. Being listed, it must be present and fresh for the execute substep to pass, as every listed output must. `quality_check.json`, `trial_meta.json` of an agreeing run and `verdict.json` are byte-shaped as on a node without an oracle. What `agree` states: the generated variant and the existing code agree, within the bound each `tests.md` judgment gives its variants, on every state variable a cross-target predicate reads, in the cases it reads that are not continuation cases (the restart test holds each of those to its base); not that either is correct (`docs/design/scale_migration.md`). The `cross-target agreement` between declared targets is unchanged: a node with an oracle and one target reads `no_comparand` there and `agree` in `oracle_check.json`.
- `perf.json` must be output as a UTF-8 `JSON object` restorable by a standard `JSON` parser.
- `perf.json` must be present and parse as a JSON object; `--stage post_execute` requires it (`_validate_raw_evidence` / `_validate_execution_json_outputs`), and on `fail` it is a `Validate.execute fail`. `quality_check.json` is the conductor's own record, written before the gate runs; no gate re-checks its presence or shape (issue #643).
- `Validate.execute` must save, in `runs/<run_id>/<node_key_safe>/raw/`, the primary evidence the verdict is evaluated over.
- The required composition of the primary evidence uses `spec.ir.yaml.io_contract.raw_requirements.required_evidence` as the canonical source. A fixed minimal composition must not be uniformly applied to all `spec`.
- When `raw_requirements.required_evidence` declares `artifact=state_snapshots` and `required=true`, `raw/state_snapshots/` must declare `variables[].name`, `variables[].shape_expr`, `time_variable`, and `time_shape_expr` in `snapshot_schema.json`; each snapshot must hold every declared variable, in every case and on every node, plus the declared `time_variable`, shape-matching its declaration — state variables their `shape_expr`, the `time_variable` its `time_shape_expr`; a rejected/guard case still emits them shape-valid — zeros of the declared extents — and must **not** drop the key. Canonical wording + correct/wrong examples: [RUNNER_OUTPUT_CONTRACT.md](../RUNNER_OUTPUT_CONTRACT.md) §3. There are two exceptions, and in both nested lists stop at the zero, so `post_execute` does not compare the shape of the empty array. One is the host-rendered driver's capture of a zero-extent case: Compile refuses a zero extent among a case's inputs unless only `xfail` tests target that case ([issue #602](https://github.com/seiya/spec2science/issues/602)). The other is a variable the node's `tests.md` `zero_extent:` line names ([issue #644](https://github.com/seiya/spec2science/issues/644), `docs/TESTS.md`): it holds no element in any record, and `post_execute` and the verdict's reader refuse one that does. The captures are **per case**: exactly one `final` record per `case.test_case_set[].case_id` (the `runner` receives each `case_id` on argv via `--cases` and commits its `final` record through the harness's capture interface; see `phase_02_generate.md`). `Validate.execute`'s deliverable gate requires each case's `final` record, as the target's capture store finds it; a file the store does not place in a case is no record (and a runner statement that names the capture directory is flagged earlier by `post_generate`).
- On a node whose runner is host-rendered (an M3c physics node), the `initial` record is a required deliverable for every case as well (Z6, issue #255): the driver's capture of the state before the first call of `step`, of the same per-case shape and checked by `post_execute` against the same schema as the `final` record (the shape gate reads every state record the target's capture store finds). The `initial` records are not `snapshot_schema.json` samples. A harness self-test commits one in the cases its `tests.md` states, and none is required of it. On a node whose IR declares `step_series`, the series is a required deliverable for every case with a `final` record, holding exactly the declared names and each row's `t`, and on a host-rendered runner its `step` column is exactly the committed steps after the `initial` record's up to the `final` record's, in order. A `history` or `restart_point` record is shape-checked in each variable it holds; which variables it holds is the driver's (a sample the variables due at its step, a restart point the restart variables), and the continuation writer refuses a restart point that lacks one.
- When `raw_requirements.required_evidence` does not declare `artifact=state_snapshots` as required, `raw/state_snapshots/` must not be required.
- When `Validate.execute` fails, the artificial generation of `perf.json` or a capture is forbidden, and the relevant `node` is `fail`.
- `quality_check.json` must simultaneously satisfy `checks.verdict_available=true` and `checks.verdict_match=true`. When any is `false` or missing, it is a `Validate.execute fail`. The conductor writes `quality_check.json` (`Conductor._author_quality_check`) and its top-level `status` is `"pass"` only when every shape holds and the serial reference's re-run itself exited 0 ([issue #674](https://github.com/seiya/spec2science/issues/674)); a quality check that does not pass fails the run (`quality_check_mismatch`).
- `quality check` execution allows only the `preset` specification of `run_quality_checks`, and forbids arbitrary command execution such as `python3 quality_check.py`.
- `Validate.execute` must not generate `test` source, a harness, an auxiliary `script`, or a temporary build control file under `runs/<run_id>/<node_key_safe>/` to establish a `quality check`. When the required artifact does not exist in the `Generate` or `Build` output, it is a `Validate.execute fail`.
- With the target profile's `toolchain.build_system=make` and a compiled `toolchain.language` (its language backend declares `COMPILED`, `registry.is_compiled_language`), the `quality check` runs with one of the build system's quality-check presets (`QUALITY_CHECK_COMMANDS` of its `build_execute`: `make_test` or `make_check`) that treats `source/<source_id>/src/` as the `project_dir`. Pass to `run_quality_checks`, through `env`, the object directory (an absolute tmp build directory), the binary directory (`binary/<source_binary_id>/bin`, absolute), the run-output directory `<abs>/workspace/tmp/<exec_agent_run_id>/qc_run`, the binary name `<spec_id>_runner`, the IR (`<abs spec.ir.yaml>`) and the case list (`"<case_id> <case_id> …"`); [CONTROL_FILE.md](../../backends/build_system/make/CONTROL_FILE.md) §1 names the variables and §2 the target. The binary name imposes the canonical binary name Build also produced, so the quality-check target's existence guard resolves the same file; the env override applies because the control file declares the name overridable. The IR and the case list impose the **same** runner argv `run_program` uses — the quality-check target invokes the binary with `--cases`, the IR and the case list, so the quality-check re-run is byte-identical in spec/case set to `run_program` and `quality_check.json` is a true value comparison; the runner **requires** `--cases` and aborts without it. Both are overridable, with defaults that keep a local build-and-test runnable standalone. The build-runtime library does not check the content of `env` (`docs/BUILD_RUNTIME.md` §Operations rules). Reference the existing binary from `binary/<source_binary_id>/bin/` (do not relink in the read-only-bound `binary/`: the quality-check target uses a **non-relinking** fail-closed guard that never re-invokes the build tool — [CONTROL_FILE.md](../../backends/build_system/make/CONTROL_FILE.md) §2 states its `make` form; a relink would rebuild a certified binary from inside the quality-check re-run). Because the quality-check target re-runs the binary and emits `perf.json` / `raw/*` directly under the run-output directory, pointing that directory at the canonical run node dir would have the quality-check binary write clobber the agent-authored `run_program` copy with provenance-mismatched output. Point it at tmp (`workspace/tmp/<exec_agent_run_id>/qc_run`, a separate subdir from `run_program`'s `run/`), and never let the binary output be written directly to the canonical run node dir. All canonical `.json` is re-authored by the agent with the `Write` tool **after both `run_program` and `run_quality_checks` complete** (the final step). Nothing other than the cross-phase audit log is written to `src/`.
- For the specification of `perf.json`, refer to `PERFORMANCE_DIAGNOSTICS.md`.
- Before `Validate.execute` completes, run `python3 tools/validate_pipeline_semantics.py --stage post_execute --pipeline-root <pipeline_root> --run-id <run_id>`, and `exit code 0` is required. `--pipeline-root` can be specified repeatedly, and in a trial where the `dependency_graph.json` sidecar's `all_nodes` holds multiple `node`, specify all `pipeline_root` corresponding to `all_nodes`. For `--run-id`, specify this trial's `run_id` to scope the verification to that run. Because `pipeline_id` is `append-only` (an existing run cannot be deleted), omitting `--run-id` would leave a broken sibling run from a past retry in the same pipeline and permanently `fail` `post_execute`. Specifying `--run-id` makes only the corrected run the verification target.

### 4-2. The implementation-quality judgment
The comparisons below run inside `Validate.execute`, after the certified run; their record is `quality_check.json`.
- The implementation-quality judgment compares every **execution shape** the binary ran in with the **serial reference**, the quality check's `make test` re-run: one process (no launcher) with one thread, and — for a launcher backend — the process grid `(1, 1)`, and — for a backend that imposes a thread-block size — the certified run's block (a kernel has no serial launch): the variables the target's parallel backend sets for a run are set to those values, so the conductor's own environment cannot widen the reference through them (`host_execution.serial_execution_env`; issue #512); a variable the backend does not set is inherited, as for every run. The shapes are the certified run's (the target profile's `execution`: `threads_per_rank`, `ranks`, `process_grid`, `block_size`) and one per member of `execution.sweep` (a process grid of `grids`, a thread count of `threads_per_rank`, a thread-block size of `block_size`), each a further `run_program` of the same binary and cases after the quality check, in a directory of its own (`target_profile.TargetProfile.execution_shapes`). Each shape is compared on two things: its host verdict over its own captures, per test (each test's `status` equal to the reference's over the reference's captures, hence to the certified shape's; no exact-equality rule over the captures, because a capture naming the ranks differs by shape by design and the predicates read the grid the run reports; `Conductor._shape_verdict`), and the captured state, under the IR's cross-target predicates — the comparison those predicates state between two targets' runs of one node holds between two shapes of one run, since the cell-wise state does not depend on how the work was divided while a reduction's summation order does (`docs/TESTS.md` §Cross-target judgment). An IR that declares none (a harness self-test, whose captures name the ranks) is compared on the first alone (`state_agreement: not_applicable`). For a launcher backend the rank count and grid the shape's harness reports in `perf.json` must be the shape's; for a backend that imposes a thread-block size, the block size it reports (`parallelism.block_size`), and on the Validate run of the target's own harness every self-test snapshot capturing `block_size` carries the certified block (`_validate_harness_reported_block`); and for a target some shape of which runs more than one thread per rank (`TargetProfile.thread_count_observable`), the thread count it reports (`parallelism.threads_per_rank`), which a harness obtains from the runtime at run time — on a target whose every shape runs one thread a constant `1` cannot be told from an observation, and the count is not compared. A sweep shape that fails to run, or any comparison that does not hold, fails the quality check, so the run records `quality_check_mismatch` (`post_execute_violation` when the `post_execute` gate also refuses the run) — a warm Generate repair. Its excerpt is the bounded tail of the report (`_execute_failure_excerpt`): the gate's report, if any, then a line per failing comparison of each shape, which come last and so survive the bound. The per-shape lines are: for the shape whose run failed, its exit status (or timeout) and the first and last lines of its stderr (`quality_check.json#shapes[].run_failure` keeps its head and tail); for each shape that did not run, the command that failed before it (a shape runs only after every earlier command succeeded, locally and at a remote site); for a state that disagrees, the case, the quantity, the value and its bound. A certified run that fails is a runtime error, as before: no shape is compared and the node is regenerated cold.
- `quality_check.json#shapes` records each shape (`label`, `threads_per_rank`, `ranks`, `process_grid`, `block_size`, the comparisons, `observed_mpi_ranks` / `observed_process_grid` / `observed_block_size` / `observed_threads_per_rank`, `launch_match` / `block_match` / `thread_match` where the target's backend and shapes ask for them, `state_agreement`) in the order the profile names them, certified first; the record's `status` is `pass` only when every shape holds and the serial reference's re-run exited 0, and a quality check that does not pass fails the run (`Conductor._author_quality_check`). A re-run that exited non-zero is named in `trial_meta.json#failure_excerpt` with its return code and the head and tail of its stderr; `quality_check.json` gains no key for it, so its `checks` and `shapes` may all hold while its `status` is `fail`. `checks` and `comparison` are the certified shape's against the reference — in `comparison` the certified run is `reference` and the serial reference is `candidate`, names kept from before the sweep; `comparison.candidate` is one process with one thread, and for a launcher target `comparison.reference.ranks` is `execution.ranks` and `comparison.candidate.ranks` is 1. `trial_meta.json#environment.sweep` records each further shape's launch, and `environment.serial_reference_env` the reference's environment.
- **The `checked` row** ([issue #589](https://github.com/seiya/spec2science/issues/589) PR-0). When the target's compiler declares checked flags (`tools/checked_build.py`, `checked_flags_for`; [phase_03_build.md](phase_03_build.md) makes the binary), the bounds-checked binary `binary/<source_binary_id>/bin_checked/<exe>` runs LAST — after every sweep shape, and only while every earlier command succeeded, so its abort cannot suppress a shape — with the same cases, in the sweep form (`run_program`, the binary's path as the record's `command[0]`), in `sweep/checked/` beside the shapes' directories, and BARE on every target: no launch prefix, one process, under the serial reference's environment (`serial_execution_env`: one thread; the grid `(1, 1)` on a launcher backend). Its row, last in `quality_check.json#shapes`, is `{label: checked, threads_per_rank: 1, ranks: 1, process_grid: null, block_size: <certified>}` (`checked_build.checked_shape`) and is compared with the serial reference like every shape — a bounds abort is a non-zero exit, `run_ok: false`, and a warm Generate repair whose excerpt quotes the runtime's diagnostic from `run_failure.stderr_head`. On a launcher target the harness reports one rank in `(1, 1)`, which is the row's `launch_match`. It is not a shape of the profile and not performance evidence. The conductor expects the row from the compiler's declaration (`checked_build.checked_shape`), never from the record; Build records the second build in `binary_meta.json#checked_build` and `Validate.execute` runs that binary, so no gate re-binds the row to it ([issue #643](https://github.com/seiya/spec2science/issues/643)). A target whose compiler declares no flag (`nvcc`: a device memory check is a launch wrapper; issue #589 PR-0 decision 3 places it with item 6 of `docs/design/scale_migration.md` §Order, which does not name it yet) runs no row and records `checked_build: null`. The row sees an access outside an array's declared bounds and nothing else: an in-bounds wrong value is the tests' to judge, a write out of bounds only in a multi-threaded path is not exercised (the row runs one thread), and on a launcher target neither is one that happens only with more than one rank (a neighbour or halo index; the row runs one process). What each compiler's flags do not bound is stated in its document (`docs/backends/compiler/<compiler>/TOOLCHAIN.md` §Checked build).
- The comparison of execution shapes is not included in the `tests` judgment target, but is handled as a `quality check`.
- On a physics `fail`, the performance evaluation is skipped.

### 4-3. Validate.post_judge substep
- The judgment canonical source is `tests.md` and `spec.ir.yaml.io_contract`.
- The judgment is performed in 2 layers: the deterministic per-test verdict (`verdict.json#per_test`, host-authored at `execute` — R2) and the dependency-aggregated `aggregate_verdict` (conductor-derived in `post_judge` — G6). No LLM judges the run in this phase.
- The start condition of `Validate.post_judge` is a passed `Validate.execute` under the target `run_id`: its `run_program` execution record, `perf.json`, the `raw/` primary evidence and the execute-authored `verdict.json` (already `∈ {pass, xfail}` — a predicate `fail` fails execute first) exist and are traceable as artifacts of the same `run_id`.
- `verdict.json#per_test` is **host-authored at `execute`** (R2), one object per `tests.md` `test_id` (set equality gated at Compile against `io_contract.tests`), each holding `test_id` + a `status` field valued one of `pass` / `fail` / `xfail` / `skipped` + a machine `basis` (`basis.predicates[]`, §4-1). `blocked` is the conductor-derived dependency-DAG outcome authored in `post_judge` (G6). The conductor's `post_judge` derivation and the `--stage pre_judge` validator consume it.
- The following are **conductor-derived in `post_judge` (G6)** — the conductor computes them correct-by-construction from `verdict.json#per_test` + the dependency set, and the `--stage pre_judge` gate re-validates `summary.counts` against `verdict.per_test`:
  - the `blocked` DAG rule: when an immediate dependency `node` is **not built+validated in its own pipeline** (the same readiness predicate the pre-launch DAG guard / the `--stage pre_judge` gate use — `_closure_node_validated_in_own_pipeline`, i.e. no binary-bound `pass`/`xfail` verdict), the upper `node` ends with `aggregate_verdict=blocked`, and `aggregate_verdict.json` records `blocked_reason` + `blocking_direct_deps`. Using the readiness predicate (not the dep's *latest* verdict) keeps a dep that regressed to a newer `fail` but keeps an older bound `pass` ready. A dep the readiness predicate admits but whose certified Validate output does not resolve through `DerivationResolver.select` (revoked or re-keyed since the gate ran, so its contribution cannot be read) is not ready either: it is `blocked`, and `blocked_reason` says its certified verdict did not resolve (issue #643). A `blocked` aggregate fails the `post_judge` substep closed (`failure_category: aggregate_blocked`) before the gate runs, so it is never certified.
  - `summary.json` holds `self_summary` + `dependency_summary` (`dependency_summary` = `total`/`pass`/`xfail`/`fail`/`blocked`), and its `counts` match the aggregate of `verdict.json#per_test`.
- On judgment-input shortage the substep fails, and the `verdict` must not be established with estimated or assumed values.
- **Dependency-DAG readiness** (before any substep of the phase). The conductor (`run_phase`) verifies every node of the pipeline's dependency set — the `dependency_graph.json` sidecar's `all_nodes` closure plus the target's harness, which the target-free sidecar does not carry (`orchestration_runtime.with_target_harness`, issue #284) — is built+validated in its own pipeline (reusing `validate_pipeline_semantics._closure_node_validated_in_own_pipeline`). A node whose `ir`/`pipeline` is not yet issued/validated terminalizes the phase `fail_closed` immediately (`validate_pre_judge_dag_incomplete`; no substep runs). A single-node run (empty closure) passes with zero overhead.
- **The `post_judge` run** (G6 derived-artifact authoring + the `--stage pre_judge` gate + severity classifier). The conductor (`_post_judge_inproc`) FIRST authors `aggregate_verdict.json` / `summary.json` / `validate_meta.json` from `verdict.json#per_test` + the dependency set (the target's harness included, `orchestration_runtime.with_target_harness`) (`_author_derived_validate_artifacts`, G6), THEN runs `python3 tools/validate_pipeline_semantics.py --stage pre_judge --orchestration-id <orchestration_id> --pipeline-root <pipeline_root> --run-id <run_id>` (scoped to this orchestration and run; orchestration-record integrity + the cross-pipeline dependency DAG) — so the gate re-validates the conductor's own `summary.counts` vs `verdict.per_test` — and records the verdict + a severity `disposition` in `post_judge_meta.json` under `runs/<run_id>/<node_key_safe>/`. The stage keeps the name `pre_judge` ("before pass-certification", §substep structure); it is run by this substep and is not a substep itself.
- A `post_judge` gate `fail` (`failure_category: pre_judge_violation`) is classified by **`disposition`**. An **unrecoverable** violation (orchestration-record / cross-pipeline dependency-DAG integrity — `agent_graph.json` / `step_result.json` / `lineage.json` / an `orchestrations/` path / the DAG markers — **or a host-authored artifact**: the execute-authored `verdict.json` or the post_judge-derived `aggregate_verdict.json` / `summary.json` / `validate_meta.json`, which a re-run would re-derive identically from the same `verdict.json`) terminalizes `fail_closed` immediately. An **unknown** violation (anything else) routes to the unified escalate LLM (the diagnostician) in prod, and terminalizes `fail_closed` in dev (fail-fast, no billed escalate leaf) — G5. Three **exit codes** are answered before the violations are classified at all, since they say the gate reached no verdict about this run's conformance: 3 (`static_frontend_unavailable`, the source-structure front end is not installed), 5 (`host_authored_artifact_violation`, a file this repository authors) and 6 (`device_kernels_absent`, a traced run that executed none of the node's kernels). (4, `stale_dependency_ir`, a stale certified IR, was removed in [issue #643](https://github.com/seiya/spec2science/issues/643) PR-5; no gate emitted it after PR-4.) 5 is not reachable from this stage as the gates stand, and 6 only if this stage and `post_execute`, which read the same trace, disagree; each is wired so it fails closed if it ever is. All three are `fail_closed`, and their violations are recorded for observation only. A DAG-readiness failure or a terminal `post_judge` `fail` is a **non-physics integrity blocker** on an *otherwise-passing* node: the node's own tests pass yet it is not certifiable in this run, so the conductor terminalizes `fail_closed` WITHOUT writing a routeable `fail` `step_result`. (A failing physics/evidence verdict is a different thing — a routeable failure handled by §Decision criteria for retry on failure, not this gate.)

## Decision criteria for retry on failure
There are two `Validate`-failure origins with distinct routing, both at `execute`; a `post_judge` failure is the non-physics integrity blocker of §4-3, not a routed origin:

1. **A deterministic per-test predicate `fail` at `execute`** (R2): `verdict.json#failure_class ∈ {physics_fail, structural_violation}`, host-authored. Attribution (`code` / `ir` / `spec`) needs reasoning, so `classify_failure` routes it to the **escalate diagnostician** in prod (which reads `verdict.json#per_test.basis`) and fails it closed in dev (F1 cross-phase-rollback posture) — except a `structural_violation` with no `predicate_error`, which the conductor routes to `Generate` (`reuse`) and which, as a backward move, terminalizes as `dev_phase_rollback` after revoking `Generate` with the failing predicates as findings. A `predicate_error` (a malformed IR predicate) is attributed to the IR by the conductor itself.
2. **A structural `fail` at `execute`** (no `verdict.json` is authored): the run produced bad or missing primary evidence, so no predicate could be evaluated. Routed deterministically to `Generate` without LLM inference, by the `trial_meta.json` failure fields below; the terminal categories of the table there fail closed instead, `oracle_disagreement` among them — a run whose own tests pass, which is no structural failure, and whose state disagrees with its `oracle` (§4-1).

The judgment input is `verdict.json#failure_class` + `per_test.basis` (origin 1) and the `trial_meta.json` failure fields (origin 2).

### Structural `execute` failure: trigger fields and `repair_strategy` (no LLM involvement)
When the structural check fails, or a run whose own tests pass disagrees with its `oracle` (§4-1), `Validate.execute` records the following keys in `trial_meta.json` as required (alongside `status=fail`). They are absent on any other outcome, so their presence means "THIS execute failed structurally, or disagreed with its oracle":

| field | range | extraction source |
|---|---|---|
| `failure_category` | `static_frontend_unavailable` / `host_authored_artifact_violation` / `device_kernels_absent` / `post_execute_violation` / `snapshot_deliverable_gap` / `quality_check_mismatch` / `oracle_disagreement` | mechanically classified by which structural input failed, or the oracle comparison |
| `failure_excerpt` | text (the tail of the `[execute fail]` report, bounded to 50 lines **and** 4000 characters) | a direct excerpt of the failing gate / gap / quality-check output |

Classification convention for `failure_category` (evaluated in this order). The first three are decided by the **exit code** `validate_pipeline_semantics --stage post_execute` answered with, and they **dominate** any co-occurring symptom, because the condition they name also fails the other inputs and no re-authored source repairs it. Below them a more specific report wins:
- `static_frontend_unavailable`: exit code 3 — the source-structure front end is not installed on the machine running the gate, so the gates that need it read nothing.
- `host_authored_artifact_violation`: exit code 5 — a violation whose subject is a file this repository authors (issue #112). Not reachable from this stage as the gates stand (its one construction site is on the `post_generate` path); wired so that the day this stage reports one, it fails closed rather than arriving as a warm retry.
- `device_kernels_absent`: exit code 6 — the traced run executed none of the kernels the node's sources define (issue #307; a target whose parallel backend declares `device_trace`).
- `post_execute_violation`: any other non-zero exit of `validate_pipeline_semantics --stage post_execute`.
- `snapshot_deliverable_gap`: a required record of a case — its `final` record, its `initial` record or its series — is missing.
- `quality_check_mismatch`: `quality_check.json#status != pass` while the `post_execute` gate passed (the serial reference's re-run exited non-zero, a sweep shape's run failed or did not run, or a shape disagrees with the `make test` serial reference in a check status, the verdict, its captured state, or in what its harness reports against the shape's own launch — under a launcher the ranks and grid, under an imposed block size the block size, and where a shape runs more than one thread the thread count; §4-2). No gate reads `quality_check.json`: the conductor decides it, and a run the `post_execute` gate also refuses records `post_execute_violation` instead; the route is the same.
- `oracle_disagreement`: not a structural failure, and decided after every input above passed and the evaluated verdict reads `pass` or `xfail`: the run's state disagrees with its `oracle`'s under the IR's cross-target predicates (§4-1, issue #680).

| `failure_category` | `repair_strategy` | basis |
|---|---|---|
| `static_frontend_unavailable` | — (terminal) | a machine problem, not a source defect: `classify_failure` fail-closes it before the `Compile`-reopen counter counts it. Recovery is the operator installing the front end, then `--resume` |
| `host_authored_artifact_violation` | — (terminal) | the leaf has no write authority over the file; the fix is in this repository's producer, then `--resume` |
| `device_kernels_absent` | — (terminal) | the measured cause is the environment: every launch of the run R4-b PR-6 certified had failed because the site's device and driver could not run the binary as built (issue #307), and a warm `Generate` retry changes neither. Recovery is the operator running a minimal kernel under the trace where the run executed (`docs/backends/parallel/cuda/DEVICE_TRACE.md` §5 gives the procedure for the local site and a remote one) and fixing the site or the target, then `--resume`; a model that launches no kernel on the cases' paths (a stub kernel beside a host loop, a branch every case takes to the host), or whose every launch fails on its own account (an invalid launch configuration), reaches this class too, and `--rederive generate` re-derives it (for a `--with-deps` closure member, run that member as the target: `--rederive` applies to the target only). The `Generate.gate` presence floor stops neither — it asks only that a kernel exist; `generate.verify` G6 is the one rule before the run, for the first |
| `post_execute_violation` | `reuse` | the gate names the offending artifact and shape; a local fix of the emitting code converges |
| `snapshot_deliverable_gap` | `reuse` | a local fix of where the runner commits the case's record |
| `quality_check_mismatch` | `reuse` | a local fix of the `test` target or of nondeterministic runner output |
| `oracle_disagreement` | — (terminal) | the host cannot tell which side is wrong — the `oracle adapter`, the `spec` or the generated code — and no leaf is shown the oracle, so a warm repair has nothing to converge on (operator decision O5, issue #680). Nothing is revoked: `Compile` and `Generate` stay certified. The operator reads `oracle_check.json` and triages: an adapter or declaration fix, then `--resume` (the build key moved, so `Build` and `Validate` re-derive); a `spec` fix with a `spec_version` bump; or a defect of the generated code, `--rederive generate`. Never a wider bound (`docs/RUNBOOK.md`) |

The `Generate` re-submission quotes `failure_excerpt` as `launches/<new_agent_run_id>.request.json#repair_findings`, and the producing `generate.generate` session is warm-resumed (`repair_strategy=reuse`), so the same leaf fixes the violation it caused. A **runner runtime error** (a non-zero exit of `run_program` itself) authors no `trial_meta.json` at all; the cause is in `stderr.log`, not in a gate report, so it routes to `Generate` with `repair_strategy=restart` (a cold re-generation). The four **terminal** categories above take neither route: `classify_failure` fail-closes them before the counter below runs, and their `failure_excerpt` is deliberately not threaded into any repair. Independently of the remaining categories, the **second consecutive `execute` failure that authors no `verdict.json`** on the same `node` — of either kind, structural violation or runner runtime error — reopens `Compile` instead of `Generate` (a `Generate` repair regenerates the runner, which cannot fix an IR-rooted mismatch, so the IR is then the likely wrong side). A per-test predicate `fail` (origin 1) is a different class and resets that counter.

`verdict.json#failure_class` is host-authored at execute (R2) and is one of `physics_fail` / `structural_violation` / `pass` (the LLM-era `runtime_error` class now surfaces as an execute structural failure with no verdict).

### Handling of Spec retry
A retry to `Spec` is not automated in the core workflow (because `controlled_spec.md` needs to be updated by hand). A defect the diagnostician attributes to the human-authored `spec` is answered with a `fail_closed` directive, which is how the run stops; on the `dev` path `tools/run_workflow.py` writes `failure_analysis.json`. The operator corrects the `spec` and starts the node again.

## Design trade-offs
- The reason for placing `execute` and `post_judge` as substeps of the same phase: "execution → pass/fail judgment" is essentially a single integrated task, and splitting them into separate phases would make the derived verdict always depend on the latest `execute` result, weakening the meaning of the phase boundary. Integrating into Validate simplifies the judgment path and makes the judgment artifacts self-contained under `run_id`.
- The reason for splitting `execute` and `post_judge` into substeps: `execute` runs the binary and evaluates this run's own tests, while `post_judge` aggregates the dependency set and certifies the run against the orchestration record, so a failure of either is classified on its own record (`trial_meta.json` / `verdict.json` against `post_judge_meta.json`).
