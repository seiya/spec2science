# Phase 2: Generate

## Overview
The phase that generates the source code of the target `node`'s `model` (physics computation) and `runner` (input/output / execution coordination). `Generate.generate` reads `controlled_spec.md` as the authority for the algorithm and `spec.ir.yaml` as the authority for the calling interface, the cases and the I/O contract (§2-1; the producer of an `infrastructure` harness node is seeded part of its spec, as stated there). The model `Generate.verify` reviewer judges the source against `controlled_spec.md` and `tests.md` and is not seeded `spec.ir.yaml`; the harness reviewer judges it against `spec.ir.yaml` (§2-2).

## Generate-executor and the leaf model
Since `M-F` the `generate-executor` is no longer selectable (`docs/GLOSSARY.md`): legacy generate execution was removed and `pure` is the only executor. `pure` is the persisted name of that executor, set against `legacy`; it does not name the leaf model, which is a `workshop leaf` since [issue #534](https://github.com/seiya/spec2science/issues/534) PR-J4-b (below). The value is still recorded in `orchestration_meta.json#invocation.generate_executor` (always `pure`) as provenance, and a resume whose recorded executor is not `pure` (a `legacy` record, or the field absent) is rejected fail-closed (`generate_executor_legacy_removed`). The authoring rules of §2-1 and the verification items of §2-2 are properties of the emitted source and hold whatever the leaf model — the `workshop leaf` of today, the `pure-function leaf` before it, or the agentic residual Z4 ([issue #171](https://github.com/seiya/spec2science/issues/171)) deleted; only the transport and the write path differ.
- Residual path: NONE. A node the producer cannot express — one with no `CodegenBundle` SHAPE at all (`Conductor._bundle_shape`), which since issue #169 is no node in the spec catalog — FAILS CLOSED: `Conductor.run_substep` emits `node_has_no_bundle_shape` and returns `fail`. It ran the shared agentic leaves with tools enabled until Z4 ([issue #171](https://github.com/seiya/spec2science/issues/171)) deleted them, so the fall-back this bullet used to describe no longer exists and was never taken in tree.
- `workshop` ([issue #534](https://github.com/seiya/spec2science/issues/534); `docs/ORCHESTRATION.md` §workshop leaf): the `Generate.generate` leaf is a `workshop leaf` — on every entry since issue #534 PR-J4-b (no `leaf:` field; before it, an entry saying `leaf: workshop` chose it over the `pure-function leaf` of the next bullet) — on the same nodes (a `CodegenBundle` SHAPE) and under the same contract: the same inputs (seeded into its `work tree` as files rather than inlined), the same authoring rules of §2-1, the same `CodegenBundle`, which the host assembles from the tree's `snapshot` and validates exactly as it validates a returned one, and the same host writes. `Generate.verify` is a reading `workshop leaf` selected by its own entry, independently of `generate.generate`'s, on every provider (§substep structure below).
- The `pure-function leaf` (history: `Z2`, from Z4 until [issue #534](https://github.com/seiya/spec2science/issues/534) PR-J4-b): the `Generate.generate` leaf read no `SKILL` and no injected must-read and returned exactly one `CodegenBundle`, every input inlined in its prompt; Claude ran it with strict tool-free isolation, Codex as `codex exec --sandbox read-only` inside the read-only `bwrap` profile. The rest of this bullet is the producer contract that leaf left to the `workshop leaf`, which receives the same documents as `seed` files of its tree. WHAT the host supplies is the shape's: on `m3c` the target IR, `<dependency_facts>`, exemplar, target profile, harness capability ABI and the host-rendered runner; on `harness` (issue #169) the runner-output contract, the legality/gate-guard section and the linter's declared rule set in place of the runner, because that leaf authors the executable entry itself. Per §2-1 the producer reads `controlled_spec.md` for the algorithm since [issue #724](https://github.com/seiya/spec2science/issues/724). A `pure-5` interim carve-out once inlined `controlled_spec.md` into the producer context to close a producer-blind / checker-sighted asymmetry against a thin `compile` roll (a step lowered to a name + I/O shape with no mathematical definition, which a tool-less `spec/`-blind leaf then had no path to, while the reviewer WAS shown it — structurally unwinnable when the IR is thin). It was **removed at `pure-10`** once the `compile`-side IR self-sufficiency guarantees landed: the strengthened lowering rule (`docs/workflow/phases/phase_01_compile.md` §IR self-sufficiency, which the host inlines into both compile prompts; it was `skills/workflow-compile-generate/SKILL.md` until Z4, issue #171) plus the deterministic `Compile.static` local-op lowering **presence floor** (`validate_pipeline_semantics._validate_local_operation_lowering`, which de-certifies the zero-signal thin-IR shape) and the `Compile.verify` V2 finding (which covers the present-but-incomplete band above the floor). (`pure-6` through `pure-9` all kept the carve-out live — `pure-8` added the runner-driven per-id checks ABI and its own removal was reverted pending the verification run; `pure-9` was an unrelated distillation.) Issue #724 seeded `controlled_spec.md` to the producer again, on its measurement of the producer and the reviewer. The `Generate.verify` reviewer reads `controlled_spec.md` by design (§2-2) — the model reviewer verifies the source against it. Because it reads no `SKILL`, the authoring rules of §2-1 that a deterministic gate (the `Generate.gate` lint / syntax / static checks) fails the source on are distilled into the launch prompt's static prefix as an `Authoring rules` paragraph; a cold-fallback repair turn re-states them (a warm resume already holds them). Rules the IR or harness capability ABI it is handed already carries are deliberately not restated there. The one rule stated there WITHOUT a gate behind all of it is the target-lowering obligation (rule 7, issue #22; issue #284 moved it from the IR's `impl_defaults` onto the target profile and the bundle's `target_lowering_plan`): its zero-directive slice is gate-enforced (the parallel backend's presence floor under §2-1's static check; for `openmp`, [GENERATE_RULES.md](../../backends/parallel/openmp/GENERATE_RULES.md) §2) and the band above that floor is held by no check: the `target_lowering_plan` is the producer's record, not a reference of the review (§2-2). It earns its place because the producer was previously punished for a rule only the reviewer had ever been told. The producer reaches the driver through the host-rendered runner source (`bundle_facts.runner_basename`; for `fortran`, [BUNDLE_BINDING.md](../../backends/language/fortran/BUNDLE_BINDING.md) §1), seeded verbatim, whose call sites are the authority for what each published operation receives, and its template states what the driver does with those operations. The model `Generate.verify` reviewer's static prefix carries the §2-2 definition of a finding (the deterministic lint/syntax/static gates already ran before it, so it covers only what the source computes against `controlled_spec.md` and `tests.md`); the harness reviewer's carries its H1–H10 checklist. Since `pure-25` the reviewer additionally receives the `#### Severity of a finding` subsection of §2-2 as a document (`severity_rubric_document`), narrowed at `pure-26` and again at `pure-27`; that subsection is the sole rule for the `issue_severity` a finding takes (issue #143). The agentic leaf is NOT handed it — no phase document is a `Generate` leaf must-read (`docs/AGENT_SKILLS.md`) — the host gives that rubric to the reviewer as `severity_rubric_document` (it reached it through a pointer in `skills/workflow-generate-verify/SKILL.md` until Z4, issue #171). After the leaf terminates, the host validates the bundle (`validate_bundle`, the post-generate gate), writes the declared files under `source/<source_id>/src/`, assembles the runner / build control file build graph, and authors `source_meta.json`. `Generate.verify` is a reading `workshop leaf` reviewing the bundle and assembled source in an independent lineage; it writes a verify verdict into its own tree, which the host projects onto `source_meta.json`. A leaf holds no repository write authority; its terminal record carries `output_refs == []` and the deliverable is vouched by the host-written artifact's on-disk existence (`docs/ORCHESTRATION.md`). Under `pure` the source directory additionally holds `codegen_bundle.json` (the accepted bundle) and `bundle_meta.json` / `verdict_meta.json` (per-attempt provenance — each superseded attempt's `per_attempt` row additionally carries the `failure_category` and a bounded `failure_excerpt` for why that turn failed, an observability field; the accepted attempt carries neither). A node with no `CodegenBundle` shape fails closed (Residual path, above); the catalog holds none since issue #169. Launch-prompt shape: `docs/workflow/LAUNCH_PROMPT_REFERENCE.md`.

## I/O contract
- execution input: `controlled_spec.md` (the algorithm), `spec.ir.yaml` (the calling interface, the cases and the I/O contract), `tests.md`
- verification input: `controlled_spec.md`, `tests.md`, the generated `source/<source_id>/src/`; the harness reviewer also `spec.ir.yaml`
- output: `workspace/pipelines/<node_key_safe>/<target_id>/<pipeline_id>/source/<source_id>/src/`, `source_meta.json`, `gate_meta.json` (the single conductor-authored `Generate.gate` deliverable; see substep structure below). Under the `pure` `generate-executor` the source directory additionally holds `codegen_bundle.json`, `bundle_meta.json`, and `verdict_meta.json` (see §Generate-executor above).

## substep structure
- `Generate.generate`: the LLM substep that generates the full source set. It returns one `CodegenBundle` the host validates and writes. (A residual agentic node read `spec.ir.yaml` and wrote `src/` directly until Z4, issue #171 — see Generate-executor above.)
- `Generate.gate`: a **deterministic** substep the conductor runs **in-process** (no leaf) between `Generate.generate` and `Generate.verify`. It runs three checkers as internal steps — a lint check, a syntax check, and a static check — and writes ONE `gate_meta.json` at the source root (`source/<source_id>/gate_meta.json`) with a `checkers` object carrying `lint` / `syntax` / `static` sub-sections, a `failure_categories` list (canonical order `syntax_error` → `lint_findings` → the static-family categories), and a composed `failure_excerpt` (per-checker sections tagged `[syntax]` / `[lint]` / `[static]`). The lint check always runs; the syntax check always runs (independent of lint); the static check runs **only when the lint check and the syntax check both pass**, so a dirty source gets the findings of the checker that read it rather than a second report; when it is skipped its checker section records `status="skipped"` and `skipped_reason="lint_or_syntax_failed"`. A gate content failure re-runs `Generate.generate` as a reopen that carries the gate's findings — warm-resuming the same leaf where the session can be resumed, else a cold repair turn in a fresh lineage seeded from the prior lineage's snapshot (`docs/ORCHESTRATION.md` §workshop leaf) — with route reason `gate_<cat1>+<cat2>+...` (e.g. `gate_syntax_error+lint_findings`). **A finding the leaf did not author is not a content failure** (issue #112): every finding is attributed to a file, and a file to an author — the leaf, or this repository, which writes the build control file and (on an M3c node) the runner glue before the leaf runs and removes both from its `allowed_output_paths`. A finding on the host-authored side terminalizes the node on the FIRST attempt with a reason naming the producer (`host_rendered_lint_findings` from the lint check, `host_authored_artifact_violation` from the static check — both in `GATE_FAILURE_TERMINAL`, both dominating a co-occurring retryable category), so the retry budget is spent only on findings the leaf can act on. A lint finding the gate can attribute to NEITHER side is `lint_finding_unattributed` and also terminal: assuming the leaf is how an unwinnable loop hides. A syntax attribution error (canary / dependency-closure, described under the syntax check) instead raises to a transport `fail_closed` with no `gate_meta.json` written, and dominates a co-occurring lint content failure. See `tools/workflow_conductor.py:_gate_inproc`, which composes `_gate_lint_check` / `_gate_syntax_check` / `_gate_static_check`.
  - **lint check** (`_gate_lint_check`): runs the build-runtime `run_linter` `preset` for the target profile's `toolchain.language` over `source/<source_id>/src/`. A lint finding is a gate content failure (`lint_findings`) — but only once it has been ATTRIBUTED. On a failing run the same declared invocation is re-run over two isolated copies of `src/`: the host-authored basenames in one, everything else in the other. The partition of the files the linter JUDGES is total, and the decision is the linter's own verdict on each half, never a read of the diagnostics text (a file name appearing in the output proves nothing, and the leaf chooses those names). One exception to the copying, not to the partition: a linter handed files by name (its `SOURCE_SUFFIXES`, the `cuda_cpp` compiler-driver linter since issue #289's R4-b PR-4) compiles the leaf's sources, which include the host-rendered header, so a host file of a suffix it is not handed is copied to BOTH halves as context. A diagnostic the compiler prints inside that header while compiling a leaf source therefore lands on the leaf half; it is held at the source instead, by the language backend's test that lints every §5.1 in the tree rendered to a header. Leaf half fails → `lint_findings`, and the repair excerpt is the LEAF half's output, so a retry is handed no diagnostic about a file it cannot write other than such a context file's. Leaf half clean, host half fails → `host_rendered_lint_findings` (terminal). Both fail → terminal, with both halves in the excerpt. Neither half reproduces the whole-directory verdict → `lint_finding_unattributed` (terminal). The probe runs pass no `command_log_path`: they certify nothing, so `<src>/command_log.jsonl` stays the record of the gate proper.
  - **syntax check** (`_gate_syntax_check`): runs the build-runtime `run_syntax_check` compiler front-end gate over the node's `src/` sources staged together with the certified dependency-closure model sources (per-compiler throwaway dir under `workspace/tmp/<agent_run_id>/syntax/<compiler>/`, isolated module scratch dir — never Build's object directory). Which files are sources, the order they are handed over, and the warning classes promoted to errors are the target language's `syntax_promotions`; the mandatory stage is the language's `bundle_facts.MANDATORY_SYNTAX_COMPILER`, whose `syntax_check` adapter builds the argv from the target profile's `toolchain.standard`, `parallel.backend` (the adapter's OpenMP flag when the value is `openmp` or combines it with another model) and `hardware.architecture` (issue #289). A language that declares no `syntax_promotions` has no stage to run, and the gate is a transport `fail_closed` for it rather than a pass-through. For `fortran` the stage and the reason for each promoted class are [GENERATE_RULES.md](../../backends/language/fortran/GENERATE_RULES.md) §2. This surfaces the whole class of syntax / standard-conformance `compile_error`s here instead of at Build. A compiler finding in the node's own source is a gate content failure (`syntax_error`). A failing stage is first attributed by re-compiling two isolated source sets with the same argv: a canary valid under every standard (a failure there means the invocation is unviable — typically a target profile `toolchain.standard` (`spec/targets/<target_id>.yaml`) the compiler driver does not accept; it is passed verbatim as the compiler's standard argument), then the staged dependency closure alone (a failure there means the closure is at fault — either a dependency's certified source is defective, since a dependency certified before a gate rule existed is not clean by induction, or this node's declared `standard` is narrower than the sound closure needs; the compiler's diagnostics say which). Both are transport `fail_closed`: the leaf authors neither the IR nor a dependency's source, so no retry of this node could clear them. Since issue #153 the closure branch is a **backstop** rather than the first line: the route that produced it in practice — a certified consumer skipped as ready and then staged against a dependency source regenerated after it was certified — is closed at readiness by the derivation key (`docs/ORCHESTRATION.md` §13a: the consumer's generate and build keys bind the dependency's selected source by output hash), which re-runs the consumer instead of letting it reach this probe. What still arrives here is a dependency source that is defective on its own terms, and a `standard` narrower than the sound closure needs. Which side of `src/` a remaining finding is on is not decided, and that is deliberate: the host-rendered driver calls the leaf-authored operations, so a diagnostic printed at a runner line can be caused by the leaf having drifted from the published signature — real, and repairable by exactly this retry. A finding that needs the runner therefore does not mean the host is at fault, and terminalizing it would convert a leaf-fixable defect into a permanent `fail_closed`. So issue #112's rule that an unattributable finding fails closed is applied to the lint check, which can partition files, and NOT to this one, which cannot; the residual — a finding caused by the runner alone — is held at the source instead by the language backend's own renderer test, which compiles and lints the rendered runner under the gate's own flags and rule set. The excerpt is likewise not narrowed to the node's own files, because an interaction diagnostic is printed at a runner line and is exactly what the leaf needs. When the mandatory stage passes, the gate re-runs it over the node's `model` file (plus its host-rendered interface header, when the language declares one) staged with the closure alone — exactly the set a dependent is staged — and a failure is a `syntax_error` content finding attributed to the leaf, logged to the canonical command log and recorded in the `checkers.syntax` stages with `scope: model_alone` (issue #389): no other file of the node's `src/` — a `helper` / `internal_module` file — is reachable from the model. A missing mandatory compiler is likewise a transport `fail_closed` (environment problem). A staged source whose NAME the tool refuses (an option-shaped name, a response file, a name that is not a source file of the language) is a gate content failure (`syntax_error`) rather than a transport one: the leaf authored the name and can rename it. No compiler runs on that path, so the stage is recorded `skipped` (there is no command to cite) and the check fails — a `skipped` MANDATORY stage never passes, so `skipped` gates here even though an uninstalled OPTIONAL target compiler does not. Optional **target-compiler stages** come from the `SPEC2SCIENCE_SYNTAX_COMPILERS` env var (comma-separated adapter ids, default the language's mandatory compiler) — a stage whose compiler has no registered adapter, whose adapter reads another language's sources, or whose binary is not installed is recorded as `skipped` and does not gate, so one configuration runs on machines with and without the target compiler. See `tools/build_runtime.py:tool_run_syntax_check`.
  - **static check** (`_gate_static_check`): runs only when the lint and syntax checks both pass; it runs `validate_workspace_root.py` then `validate_pipeline_semantics --stage post_generate` over the generated source. These are the purely-static gates the `Generate.verify` leaf used to own; running them here means the LLM `Generate.verify` pass is reached only on a deterministically-clean source. A violation is a gate content failure — unless its SUBJECT is something the leaf has no write authority over: a file this repository authors, which on an M3c node the host-rendered runner gates are given nothing but, marked by the validator by TYPE and answered as a dedicated exit code (5, `host_authored_artifact_violation`, terminal), on which alone the conductor classifies, never on the text. The node's own certified IR is not re-read here: readiness (`check-phase-certified`'s compile clause, `docs/ORCHESTRATION.md` §13c) runs the current `--stage compile` validator on it before any skip of `Compile`, so the stage's io_contract re-read and its exit code 4 (`stale_dependency_ir`) went in issue #643 PR-4. A node whose runner the leaf really does author (the `infrastructure` harness self-test, the `harness` bundle shape) keeps the ordinary content failure — there the runner is declared bundle content, so the host authors none of it. When the check is skipped (lint or syntax failed) its section records `status="skipped"` / `skipped_reason="lint_or_syntax_failed"`. Among those gates is the parallel backend's **presence floor** (`parallel_directives`, `_validate_parallel_presence_floor`, issue #22): on a `component/` / `problem/` node whose target's parallel backend states a floor for the target's (language, hardware class) (which pairs it states one for, and how a directive is recognized, are the backend's: `docs/backends/parallel/<backend>/GENERATE_RULES.md`; for `openmp`, the `!$omp` presence floor of [GENERATE_RULES.md](../../backends/parallel/openmp/GENERATE_RULES.md) §2) **and whose bundle's `target_lowering_plan.parallelization` does not explicitly decline that model**, a model source carrying counted loops must carry at least one directive of the model. The floor's pieces are the backends' (issue #289, R4-b PR-3): the parallel backend says when it applies, how a directive is spelled and when a plan declines it; the language backend counts the loops (`source_reading.counted_loops`). The target's parallel backend is the default model: only a `model` member that names `none` (or another model) exempts the node, and a plan with no `parallelization` or no model member does not. On a target whose `parallel.backend` combines several models (issue #700) every member's floor is asked, and a plan exempts the node from one only when its model names none of the members, so a plan that names one member leaves the other members' floors in force. The exemption has to be a declaration because the plan is the reopened leaf's OWN (issue #284; until R4-a PR-3 the exemption was the IR's Compile-authored knob, which the Generate leaf could not edit), so reading silence as an exemption would let the producer switch its own floor off; whether a declared `none` is honest is held by no check (no wrong value follows from it, and the thread and rank comparisons of `Validate` hold the values). It is a floor in the same sense as `Compile.static`'s local-op lowering floor — it decides only the unambiguous case (the profile names a parallel backend that states a floor, there are loops to parallelize, and there is not one directive anywhere) and is fail-open in every other direction: whole-array sources, a target whose parallel backend states no floor for its pair, a source tree with no readable bundle, and `infrastructure/` nodes (host measurement code) all pass, and so does a source the language backend reads as already parallel or cannot classify (`source_reading.counted_loops` answers 0). What counts as already parallel, and how a source is read for the floor, are the backends': for `openmp` over `fortran`, [GENERATE_RULES.md](../../backends/parallel/openmp/GENERATE_RULES.md) §2 and the language's [GENERATE_RULES.md](../../backends/language/fortran/GENERATE_RULES.md) §4 (line-anchored detection, and the three fail-opens that buys). **A genuinely non-parallelizable node is out of scope by declaring `"model": "none"` in its plan's `parallelization`** — the violation says so, and the producer that reads it is the one that wrote the plan, so the fix is a plan change, not a directive the producer does not believe in. Whether that declaration is honest over the node's loops is held by no check. Everything above the floor — *which* loops are parallelized, whether the schedule matches the plan — is the producer's choice and is held by no check either: the plan is not a reference of `Generate.verify` (§2-2), which finds a parallel construct only when it makes a returned value wrong. For an MPI target (issue #316) the floor is a whole-node judgment the parallel backend states itself (`PresenceFloor.node_violations`), over the model sources and without counting loops, and a plan that declines MPI exempts nothing from it (the host-rendered driver distributes each case whatever the plan says, issue #610): no source reaches the message-passing library directly, a `component`'s model sources name no harness operation, and the plan declares `state_residency: distributed`; a `problem` is not asked for a halo-exchange call (issue #716 F-1). [GENERATE_RULES.md](../../backends/parallel/mpi/GENERATE_RULES.md) §2 is canonical for it and for the source rule that comes with a distributed harness (a physics `use` of the harness limited to its distributed-state operations).
- `Generate.verify`: an independent LLM substep that verifies what the source computes against `controlled_spec.md` and `tests.md` (the model reviewer) or against `spec.ir.yaml` and the runner-output contract (the harness reviewer), §2-2. It launches **no** validator gate (those are the `Generate.gate` static check's, above); it performs only the LLM semantic checks. It is a reading `workshop leaf` (`docs/ORCHESTRATION.md` §workshop leaf: the bundle is seeded as `bundle_manifest.yaml` plus each file at its `logical_path`, and the verdict is written as `verdict.json` in its tree), reviewing the bundle and assembled source; its verify verdict is what the host projects onto `source_meta.json`, whose `last_fail_reason` is the verdict's reason followed by a numbered list of every `findings[].summary`.

## `source_id` format
- Format: `src_<YYYYMMDD>_<seq3>`, e.g. `src_20260511_001`

## `source_meta.json` required keys
- Common: `attempt_count`, `verification_status`, `last_fail_reason`, `debug_mode`, `context_isolated`
- When `context_isolated=false`, `constraint_reason` is required.
- `artifact_hashes`: stamped by the host at `write-step-result` on a `pass` (NOT authored by any leaf) — the sha256 of each of this phase's declared deliverables. It is what makes the phase `certified` (`docs/GLOSSARY.md`), so an artifact edited afterwards is refused and the phase re-derives. Canonical: `docs/CLI_REFERENCE.md#write-step-result`.
- `output_hash`, `derivation_key`, `derivation_inputs`, `derivation_transformation`: stamped beside `artifact_hashes` on a `pass` ([issue #250](https://github.com/seiya/spec2science/issues/250)) — the output's content hash and the `derivation key` (`docs/GLOSSARY.md`) the attempt ran under. The phase's deliverables — and so `artifact_hashes` — include the host-rendered runner and the build control file since that issue: they are what Build compiles.
- `lint_command_ref` is no longer recorded by the leaf: lint is the deterministic conductor-run `Generate.gate` lint check, whose result is `gate_meta.json`'s `checkers.lint` section.

## substep details

### 2-1. Generate.generate substep
- `Generate` runs per `node` and generates source dedicated to the target `node_key`.
- The `generate substep` generates `source/<source_id>/src/` and `source_meta.json`.
- `Generate.generate` is seeded the node's `controlled_spec.md` ([issue #724](https://github.com/seiya/spec2science/issues/724)). The Controlled Spec is the authority for the algorithm — what is computed, its guards and refusals included; `spec.ir.yaml` is the authority for the calling interface (the published operations, their signatures and ranks), the cases and the I/O contract. Where the two differ on what is computed, the producer follows `controlled_spec.md`. The IR stays seeded: it is the default case file of the `run` operation, the source of the published operations, and what the `Generate.gate` checks read. (History: a `pure-5` interim carve-out inlined `controlled_spec.md` into the producer's context and was removed at `pure-10`; see the Generate-executor section above.)
- **The harness producer: the producer of an `infrastructure` harness node is seeded §1 to §4 and §6 of its own `controlled_spec.md`, not the whole document** ([issue #644](https://github.com/seiya/spec2science/issues/644): the operator's decision recorded there names §3 and §4; §1, §2 and §6 are seeded with them because §3 and §4 cite §2, the distributed harness's §3 cites §1, and §6 holds prohibitions the reviewer holds the source to). A harness's contract is the behaviour of each published operation and of its self-test in each case, which its IR's `algorithm` does not carry in full: an audit of the three harness specs against the producer's seeds found rules stated in no seed on every one of them, and restating each in a seeded document had left the next omission to be found in review. The seed is the spec from its responsibility and scope through its failure conditions, and its prohibitions, verbatim (`Conductor._build_leaf_harness_context`); §5, the published surface, stays the IR's `public_api`. The whole document, as the bullet above states, is seeded for every `component` and `problem` node.
- **M3c host-render scope (R1/M3c-β → M3d).** On an *M3c node* (a physics node whose target's build system and language both declare `control_file` and whose language declares `runner_render` — today `fortran` and `cuda_cpp`; the harness it runs over is the target's, `spec/targets/<target_id>.yaml` `harness`, issue #284) the `runner` is **host-rendered by the conductor**: the leaf authors the `<spec_id>_model` source alone (the published operations of the IR's `public_api.signatures`; the file name is the language's `bundle_facts`), and the `<spec_id>_runner` source, the driver ([docs/workflow/RUNNER_OUTPUT_CONTRACT.md](../RUNNER_OUTPUT_CONTRACT.md) §3 states what it writes), / the build control file (for `make`, `src/Makefile`: [CONTROL_FILE.md](../../backends/build_system/make/CONTROL_FILE.md) §1) — with, for a language whose sources include host-rendered headers, those headers — are NOT in its write set. The runner-output and build-control-file bullets below then describe the **host-rendered** output, not a leaf write; they apply as **authoring** rules only to a runner-authoring leaf — an `infrastructure` self-test runner, the only remaining one. Since issue #169 that leaf is PURE too: it produces a bundle of the `harness` shape (the `runner` role of bundle `1.1.0`) and receives `RUNNER_OUTPUT_CONTRACT.md` inlined whole in its prompt rather than force-read. It is NOT injected for an M3c physics generate leaf (node-aware; see `AGENT_SKILLS.md` / `leaf_contract_doc_refs`).
- Regardless of language, generate `model` (physics computation) and `runner` (input/output / execution coordination) separately.
- **The seeded documents are the whole behavior** ([issue #417](https://github.com/seiya/spec2science/issues/417), [issue #724](https://github.com/seiya/spec2science/issues/724)). The producer implements what `controlled_spec.md` and `spec.ir.yaml` state — with the tests and the contracts seeded in its work tree — and nothing beyond it: an input rejection, a validation, an early termination or a call that none of them states is an addition, and so is an operation the spec or the IR restricts to some cases widened to run on every case. Where `controlled_spec.md` fixes how an invalid input is handled, the producer follows it; where it is silent, the producer adds nothing. Two things are not additions on the producer side: what another rule of its prompt requires of the source (the inert dummy binding and an inert dependency call; on an M3c node also what the target fragments require, on the `harness` shape also what the inlined gate guards and static lint rule set require), and reporting a failure the runtime itself returns (an I/O, allocation, device-call or argument-retrieval status) where that report changes no answer for an input the IR accepts (on the default shape: the Controlled Spec accepts). Both `Generate.generate` templates carry this obligation (rule 8 on an M3c node, rule 12 on the `harness` shape, which names the IR and the seeded sections of the spec). On the reviewer side, the model reviewer's finding is an added operation or branch that changes a returned value or that `controlled_spec.md` forbids — an added rejection of an input the spec accepts is one (§2-2); on the `harness` shape H4 fails an operation, iteration, branch or dependency call the IR omits, and exempts only the binding, so the producer's wider carve-outs have no sentence there.
- The `runner` calls the `model` via `call` / `use` / `import`, and must not duplicate the physics-update logic (on an M3c node the caller is the host-rendered driver).
- **Runner program output** (`perf.json` / `raw/` composition, per-case snapshot naming, forbidden judge-artifact filenames, and the JSON serialization rules — a language's writer rules are its backend's, `docs/backends/language/<language>/RUNNER_OUTPUT.md`) is canonical in [docs/workflow/RUNNER_OUTPUT_CONTRACT.md](../RUNNER_OUTPUT_CONTRACT.md) — the contract of a **runner-authoring** `Generate.generate` leaf (per the M3c scope above, that is an `infrastructure` node — which receives it whole, as `runner_output_contract_document`: inlined in its pure prompt from issue #169, a `seed` file of its tree since issue #534 PR-J4-b; an M3c physics leaf authors no runner and neither reads nor receives it). The bullets below restate it for this phase's context; on any divergence, `RUNNER_OUTPUT_CONTRACT.md` governs.

- **The `<spec_id>__` prefix marks the node's published surface.** For a `spec_kind: infrastructure` node that surface is exact: the `operation_id` entries of `public_api.published_operations[]` plus the derived types of `public_api.published_types` (both prefixed). A `spec_kind: component` node's surface is exact in the same way, and since issue #153 that includes its SIGNATURES: the `operation_id` entries of `public_api.published_operations[]` (V8 pins them == controlled_spec §5, and `signatures` / `module_parameters` == §5.1), and the deterministic `Generate.gate` check `_validate_component_generated_surface` pins the generated `<spec_id>__` published-procedure set (read through the language's `source_reading`; for `fortran` the `subroutine`s, [GENERATE_RULES.md](../../backends/language/fortran/GENERATE_RULES.md) §3) == exactly that list (a missing published op, or an extra `<spec_id>__` procedure, reopens `Generate.generate`). A `problem` node publishes `<spec_id>__step` and, when §5.1 declares it, `<spec_id>__init` ([issue #589](https://github.com/seiya/spec2science/issues/589)): `_validate_generated_signatures` pins each signature against the model and the bundle's `operation` entrypoints must equal the list, while `_validate_component_generated_surface` stays `component`-only, its subject being the name set a consumer calls, so an extra `<spec_id>__` procedure of a `problem` is held by no gate; the intermediate `algorithm.steps[].operation_ref` names are **not** published. An internal helper procedure takes a **bare** name. A public procedure carrying the `<spec_id>__` prefix that is outside the published surface on a `problem` is a `Generate.verify` finding only when it changes a returned value (§2-2).
- For a node whose `spec_kind` publishes an exact surface (`infrastructure`, and `component` since issue #153), the `model` must publish every `public_api` symbol with the signature its IR `public_api.signatures[].signature` describes (the language-neutral structured `{symbol, signature}` form, which the leaf renders into the target language) — same argument names, order, types, ranks, `intent`s, `result` name, and (for a published derived type) component layout. The IR's `public_api.signatures` (which Compile transcribed from the controlled_spec §5.1 canonical interface block and the `--stage compile` gate pinned == §5.1) is the producer's authority for the signatures (§2-1). The deterministic `Generate.gate` static check (`validate_pipeline_semantics --stage post_generate`, `_validate_generated_signatures`) renders §5.1 through the target language's `signatures` backend and requires each published symbol's declared characteristics in the model source (`bundle_facts.model_basename`) to equal the pinned ones — what a symbol is compared by, which spellings of one declaration compare equal, which declaration counts as a definition and how a prototype is declared are the language's (for `fortran`, [GENERATE_RULES.md](../../backends/language/fortran/GENERATE_RULES.md) §6); an argument-name / type / rank / `intent` / `result` / component drift reopens `Generate.generate`. **Presence of the header is not enough: each published procedure must also be DEFINED** — the same check requires the pinned header to belong to a module-level procedure DEFINITION, so a prototype (a declaration with no body, or a procedure contained within another procedure) that carries the header verbatim is refused and reopens `Generate.generate`. Before that check the line comparison accepted it: the module compiled, the node's own Build linked, and the failure surfaced as `undefined reference` at a CONSUMER's link, one node and one billed phase later. The definedness question is asked of the language backend's structure front end, so a source it cannot resolve is a `Generate fail` naming the rename to make — skipping it instead would put the check behind a switch the leaf holds. This moves signature-exactness off the `Generate.verify` leaf (and the Build link error) to a cheap deterministic check. **The rule runs the other way for a §5.1 `interfaces` prototype (issue #266): the IR's `public_api.interfaces` entries are the shapes of procedures a CALLER passes, so the `model` must DECLARE each one as a prototype (a declaration with no body) with the entry's argument set exactly, and must NOT define a procedure of that name** — a missing prototype, a drifted one, or a defined one reopens `Generate.generate`; a prototype the source declares that the IR does not is private and unchecked. The IR's `public_api.module_parameters` (which Compile likewise transcribed from §5.1 and the `--stage compile` gate pinned == §5.1 by value) is the producer's authority for the module-parameter values (`dp` / `case_id_len`) in the same way; the leaf declares each as a named constant of the model module in the target language's declaration form (an accessibility attribute on that declaration is outside the pin — the harness `controlled_spec.md` §3 leaves export free, and each component §5.1 block says the attribute is immaterial — and the same holds for the renderer's harness pin), **lowering the neutral IR kind value to its target-language spelling** (the IR carries `float64`); the `Generate.gate` static check renders §5.1's neutral parameters through the same language backend and value-pins those declarations against the model source, so a dropped or drifted parameter value — or a leaf that emits the neutral kind token verbatim instead of the language's spelling — reopens `Generate.generate`. The declaration form, the attribute the pin ignores and the kind spelling are the language's (for `fortran`, [GENERATE_RULES.md](../../backends/language/fortran/GENERATE_RULES.md) §6). **A certified IR compiled before the current contract** (one whose `public_api` lacks a surface §5.1 declares, or whose `io_contract` a later rule rejects) is not re-checked at `Generate.gate`: `check-phase-certified`'s compile clause re-runs the current `--stage compile` validator — the same `public_api` == §5.1 pins and io_contract reader — on a certified IR before any skip of `Compile`, and refuses one it rejects (`docs/ORCHESTRATION.md` §13c), so `Compile` re-derives it. The `Generate.gate` stale-IR guard and io_contract re-read that repeated those readers (issues #153 PR-2 and #238) went in issue #643 PR-4. A DEPENDENCY's certified IR is not re-validated by readiness (§13c states the scope line).
- **Inert dependency call.** Each dependency `operation` is judged individually by whether `spec.ir.yaml` declares a sink for its results. An operation whose result corresponds to a variable in any `algorithm.steps[]` entry (`inputs` OR `outputs` — a result can flow straight from a step's `outputs` to an `io_contract` output with no intervening `steps[].inputs` reference), to a `derived_field_rules` / `invariants` quantity, an `io_contract` output, or a `semantic_dependency.required_sources` variable is **load-bearing**: its results are bound to those declared variables and flow exactly as declared (IR variable names carry no provenance marker, so the correspondence is resolved from the step semantics; an uncertain correspondence is treated as load-bearing). Only when no such sink exists — every declared output is computable from the case/request facts and the node's own step outputs (the shape it covers is a `component` or `problem` dependency, whether the closure or `deps.yaml` put it in `direct_deps` — the IR does not distinguish them) — is the call authored **inert** (`docs/GLOSSARY.md`): every actual argument is a local variable assigned before the call, and no call result reaches an `io_contract` output, a snapshot variable, or an `algorithm.invariants` quantity. An invented purpose for an inert call — a probe configuration, an acceptance threshold or tolerance, a validity/binding flag folded into an output, a conditional branch on the call's results — is an execution path no seeded document states, and a `Generate.verify` finding where it changes a returned value (§2-2). The inert form does not collide with the deterministic gates: an actual assigned before the call is not counted as a dependency result by the `Generate.gate` static-check dependency-dataflow gate (which also scopes to `problem/` nodes), and a variable passed as an actual argument is a use for the `Generate.gate` syntax-check unused-variable gate.
- **The build control file.** Who authors `src/<control file>`, and what it must say for Build and `Validate.execute` to drive it, are the target build system's: `docs/backends/build_system/<build_system>/CONTROL_FILE.md` (for `make`, [CONTROL_FILE.md](../../backends/build_system/make/CONTROL_FILE.md)). For a target whose build system and language both declare `control_file` the conductor authors it host-side, for leaf and dependency nodes alike, and it is not in the generate leaf's `allowed_output_paths`; the rules there are what that authored file satisfies, and what a leaf-authored one would have to. The `post_generate` gates over it are the build system backend's (`control_file`), with the module-dependency facts asked of the language's `source_reading`.
- Within the same `pipeline`, the same `src` must not be copied to a different `node_key`. Make commonization explicit as a common library.
- The target profile is an obligation on the generated source, not description, and the lowering onto it is the producer's own decision, declared in the bundle's `target_lowering_plan` (issue #284; until R4-a PR-3 the IR's Compile-authored `impl_defaults` knob layer carried it): the parallelization choice as `parallelization: {model: <openmp|none|…>, …}` with the loops it covers and any schedule / chunk / collapse, and every other choice under one of the plan's closed optional keys (`data_layout` / `decomposition` / `communication` / `accelerator_mapping` objects, and `fusion`, whose groups fuse `optimization_unit` members, not loops; a loop fusion, tiling or vectorization inside the node is a member inside one of the objects). An other-named key is refused. The source does what the plan states. Where the plan is silent the default lowering is the target's parallel backend's, and so is what already counts as parallel: `docs/backends/parallel/<backend>/GENERATE_RULES.md` (for `openmp`, [GENERATE_RULES.md](../../backends/parallel/openmp/GENERATE_RULES.md) §1). The default is a recommendation, not a rule: beyond the backend's presence floor (§2-1's static check) the choice is the producer's, stated in the plan. Never force a directive onto a non-parallelizable loop (declare `model: none` and say why).
- When the physics update cannot be implemented, it is a `Generate fail`, and a fixed string or fixed `JSON` must not be output as a substitute.
- `static lint` of record is NOT run by the `Generate.generate` leaf. A `workshop leaf` may run the same lint through its wrapper (§Generate-executor) as feedback, and no gate reads that result. The `static lint` the phase is judged by is the deterministic `Generate.gate` lint check the conductor runs in-process over `source/<source_id>/src/` as `project_dir`, with the `run_linter` `preset` the linter backends declare for the target profile's `toolchain.language` (`registry.linter_for_language`: each linter backend's `lint` module lists its `LANGUAGES`; the `mixed` composite yields two pieces of evidence, one per linter it runs). It is not run via a `lint` target of the build control file or via `compile_project`. The conductor calls the build-runtime library (`docs/BUILD_RUNTIME.md`) in its own process, so no server registration or tool permission is a workflow-start premise.
- **Language rules.** The idioms that make a source pass the `Generate.gate` lint check and syntax check on the first attempt — the linter's rule idioms and the compiler front-end's standard-conformance rules — are the target language's: `docs/backends/language/<language>/GENERATE_RULES.md` (for `fortran`, [GENERATE_RULES.md](../../backends/language/fortran/GENERATE_RULES.md)). A finding reopens `Generate.generate` and costs a regenerate cycle. The rule set the lint check applies is declared in the linter backend (`tools/backends/linter/<linter>/lint.py`), and it is imposed with allow directives disabled, so an allow comment suppresses nothing.
- **The `problem` model gates.** On a `problem` `node` the `Generate.gate` static check reads the model source with the target language's `source_reading` (issue #289, R4-b PR-3) and holds it to three gates: every dependency operation's result must reach the node's declared outputs through an assignment chain, outputs may not be literal-only, and a multi-dimensional node may not be a metric-only scalar kernel (a `<spec_id>__init` that only calls a member's `__init`, as the next bullet requires, is not one). How a source states its outputs, and the forms the gates refuse with a rewrite instruction, are the language's: `docs/backends/language/<language>/GENERATE_RULES.md` §5 (for `fortran`, [GENERATE_RULES.md](../../backends/language/fortran/GENERATE_RULES.md) §5). Canonical authoring rule: `tools/prompt_templates/workshop_generate_generate.txt` and the language's prompt fragment.
- **A member `problem`'s `__init` (the system tier, Part 2).** On a `problem` `node` whose dependency `problem` publishes `<member>__init` (its `operations` in the IR list it), the model's `<spec_id>__init` calls the member's `__init` in its own body (a call in a contained procedure it never calls does not count), and the bundle names the member's `__init` NOWHERE ELSE: not from `<spec_id>__step` or any other procedure, not through an imported local name used elsewhere, a procedure pointer, an actual argument or an interface, not in another source file. That the call runs once for every case is the rule (`docs/CONTROLLED_SPEC.md` item 5's private state) and not the gate's: a call skipped on a later case is the repeat case's to see. The model never calls its own `<spec_id>__init` either: the driver calls it once per case, in every process, a continuation case's included. Both halves hold together, and the `Generate.gate` static check refuses each (the language's `source.validate_member_init_placement`; the language's spelling of the admitted call is its `GENERATE_RULES.md` §3, and the producer is told it by the language's prompt fragment, rule (4)). The private-state rule reaches the producer through `workshop_generate_generate.txt` and the model reviewer through the verify template's definition of a finding (§2-2), each with the reuse-storage exemption. No value the model keeps outside the schema — the member's private state included — may depend on an earlier `__step` call, an earlier case, or whether the process ran the case from step 0: the continuation case runs in a process of its own and judges exactly that.
- **The source-isolation gate.** On every M3c node (`problem` and `component`) the `Generate.gate` static check reads every leaf-authored source with the target language's `source_reading` (`model_harness_isolation_violations`) and refuses a source that uses the harness (a distributed harness's own operations excepted, `docs/backends/parallel/mpi/GENERATE_RULES.md`), does file I/O, or holds a literal naming a file only the host writes. The driver reaches an operation by construction, through the `use` and the `call` it renders, so no gate reads for that reach; the signature pin holds what it calls. What each language reads is `docs/backends/language/<language>/GENERATE_RULES.md`.
- `Generate` must include in its official output a preset-compatible quality path with which `Validate.execute` can run using only the `preset` of `run_quality_checks`. On shortage, it is a `Generate fail`.
- With a build system whose control file carries the quality-check presets and a compiled `toolchain.language` (its language backend declares `COMPILED`, `registry.is_compiled_language`), the control file must define the test target the preset runs, and that target must run the existing binary without relinking it and exactly as `run_program` does; on absence it is a `Generate fail`. The rule, and the recipe that satisfies it, are the build system's: for `make`, [CONTROL_FILE.md](../../backends/build_system/make/CONTROL_FILE.md) §2.

### 2-2. Generate.verify substep
The `post_generate` static gate is **not** run by `Generate.verify`. The conductor's deterministic `Generate.gate` substep — the syntax check (the compiler front-end gate) and then the static check running `validate_workspace_root.py` then `python3 tools/validate_pipeline_semantics.py --stage post_generate --pipeline-root workspace/pipelines/<node_key_safe>/<target_id>/<pipeline_id>/ --source-id <source_id>` (`exit code 0` required) — runs **before** `Generate.verify`; a violation reopens `Generate.generate` and `Generate.verify` never starts. So verify is reached only on a deterministically-clean source and performs only the LLM semantic checks below.

`Generate.verify` runs none of the build-runtime entry points (`run_linter` / `run_syntax_check` / `compile_project` / `run_program` / `run_quality_checks`): it holds no tool that runs one — a reading `workshop leaf` is served no wrapper operation (`static lint` is the `Generate.gate` lint check and the compiler syntax gate is the `Generate.gate` syntax check, both conductor-run). `Generate.verify` launches **no** external validator gate: `validate_workspace_root.py` and `validate_pipeline_semantics --stage post_generate` both run in the conductor's `Generate.gate` static check, which runs only after the conductor's own lint and syntax checks have passed. `Generate.verify` authors nothing: it is a reading `workshop leaf` that writes a verdict into its own tree, and the host projects it onto `source_meta.json` after the child window closes. It inspects the producer sources and cannot rewrite them — it reads copies seeded into its own tree, under an empty tmpfs at the checkout path — so a `command_log.jsonl` side output under `src/` is impossible rather than refused after the fact. (Until Z4, [issue #171](https://github.com/seiya/spec2science/issues/171), the same property came from an `allowed_output_paths` of exactly that one file plus a per-file `bwrap` `write_root`.)

`Generate.verify` judges by reviewer shape ([issue #724](https://github.com/seiya/spec2science/issues/724)):

#### The model reviewer: a spec-relative review
On every node whose bundle shape is the default (`component` and `problem`), the reviewer's reference is the node's `controlled_spec.md` together with its `tests.md`, and it judges what the source COMPUTES against what they state. It is not seeded `spec.ir.yaml`: the published interface it reads is the spec's §5.1 and, for each dependency operation, `DEPENDENCIES.md`. The template (`tools/prompt_templates/workshop_generate_verify.txt`) is canonical for the wording; what it holds is:
- **A finding** is a numerical or semantic disagreement between what the source computes and what `controlled_spec.md` states: a different formula, sign, factor or constant; a different iteration limit, convergence threshold or test; a branch condition or order of operations that changes a returned value; a missing operation, or an added one that changes a returned value or that the spec forbids; a refusal, non-convergence or failure behaviour that differs from the spec; state carried between calls that the spec does not allow (on a `problem` `node`, a value kept outside the arguments that depends on an earlier call or an earlier case, rather than established by `<spec_id>__init` from the current case's inputs or set by `__step` from its own arguments before it is read; storage kept only for reuse is not such state); and a dependency call whose arguments do not match, in order and rank, the published interface `DEPENDENCIES.md` lists.
- **Not findings**: style, naming, comments, code structure, parallelization or performance — a source parallelized, scheduled, laid out, fused, tiled or vectorized differently from its `target_lowering_plan`, or not at all, is not a finding; only a construct that makes a returned value wrong (a data race, an uninitialised read) is, and one the parallel backend's paragraph names because it hides a race from `Validate`'s thread comparison —, the target language's binding of an intentionally-unused dummy, the build and interface binding (checked by `Generate.gate`), and the floating-point range of an expression the spec itself states.
- **Degenerate inputs.** The reviewer works out, by reading the source, what each procedure the driver calls does for every invalid or degenerate input the spec's guards concern, and compares it with the specified refusal.
- **The driver.** The host-rendered driver hands every call the whole case unless the target's parallel backend partitions it; on such a backend its own paragraph says what each call receives and which defects make a returned value wrong there, and names any construct that is a finding there although it makes no value wrong (`tools/prompt_templates/backends/parallel/<backend_id>/generate_verify.txt`). The `target_lowering_plan` is the producer's record of how it lowered the computation and is not a reference of the review: the deterministic floors of `Generate.gate` (above) and the thread and rank comparisons of `Validate` are what hold the lowering.
- **The input side.** Where `controlled_spec.md` and `tests.md` contradict each other on what the source must compute, the finding names that input and the rubric below grades it.

#### The harness reviewer
On a harness-shaped node (`infrastructure`), the reviewer keeps the IR: it judges the model and the executable entry against `spec.ir.yaml` and the runner-output contract by its own checklist (H1–H10, `tools/prompt_templates/workshop_generate_verify_harness.txt`), and grades by the same rubric.

#### Severity of a finding (`issue_severity`)
`issue_severity` names the repair a finding calls for. The conductor acts on the value as `docs/workflow/WORKFLOW_CORE.md` states; the value does not grade the consequence the defect would have at `Validate`, and the size of the correction does not change it. One question selects the value: whether `Generate.generate`, re-run with the finding and the same inputs, can resolve the finding.
- `minor`: the defect lies in the sources under review, and `last_fail_reason` names a correction that makes them agree with what the reviewer's template holds the code to. Every finding whose subject is the generated code takes this value — a different formula, sign, factor, constant, limit or threshold, a result-changing branch or order, a missing or added result-changing operation, a refusal or failure behaviour that differs, state carried between calls, a wrong argument order or rank in a dependency call — except the one `critical` names.
- `major`: no re-run of `Generate.generate` from the same inputs can resolve the finding. The subject is an input rather than the sources under review: `controlled_spec.md` and `tests.md` contradict each other on what the sources must compute; or, for a reviewer seeded `spec.ir.yaml`, the IR drops or distorts a requirement that `controlled_spec.md` or `tests.md` carries, or lacks what a checklist item requires the code to reflect. `last_fail_reason` names the input and the contradiction.
- `critical`: the sources under review cannot serve as the base of a repair: they are not this `node`'s, or the `model` implements a scheme other than the one the reviewer's template holds the code to, as a whole rather than diverging in a step.
- When the reviewed documents do not settle whether the subject is the sources under review or an input, the value is `minor`. When they do not settle whether the sources under review can serve as the base of a repair, the value is `minor`: the repair the finding calls for is a producer re-run either way, and only a subject on the input side earns `major`.

## On-failure behavior
- A `Generate fail` retry defaults to an in-phase retry.
- A `Generate.verify` `major` names an input (§Severity of a finding). In `dev` the conductor terminalizes it (`dev_verify_major`); in `prod` it escalates (`verify_severity_major`). What the operator or the diagnostician repairs depends on the input it names. When it is `spec.ir.yaml` — which only the harness reviewer, the one reviewer seeded the IR, can name — the repair is a re-derivation of `Compile`: by hand in `dev` (`docs/RUNBOOK.md` §3-1); in `prod` a diagnostician directive that reopens `Compile` revokes the certified IR with the verdict's `last_fail_reason` as the revocation's findings, then runs `reset-phase --from-phase compile`; the revocation is what makes `check-phase-certified` refuse the stale IR, and `Compile` → `Generate` re-run. The findings reach `Compile.generate`'s prompt on a `reuse` directive repairing an attempt this orchestration launched, and stay on the revoked `ir_meta.json` otherwise; `Generate` re-runs from its full launch prompt. Canonical: `docs/CLI_REFERENCE_RARE.md#revoke-artifact`, `docs/RUNBOOK.md` §3-1. When it is the model reviewer's `major`, the finding names a contradiction between `controlled_spec.md` and `tests.md`, which no re-derivation repairs: the operator corrects that input and starts the node again.
